## 追加（下午）：WSL 资源限制导致 openclaw 故障 → 已修复

**现象**：钦友反馈上午的 WSL2 资源限制后，WSL 里的 openclaw 无法回复消息。

**根因定位（第一性原理）**
- 上午我在 `.wslconfig` 写入 `memory=4GB / processors=4 / swap=2GB`。
- **主因是 CPU**：本机 **16 核**，`processors=4` 砍掉 75% 算力；openclaw 的并发上下文处理/本地推理严重受限。
- 次因：`memory=4GB` 压在 openclaw 低配线上（官方口径 Windows+WSL2 建议 6GB 起）。
- 证据链：
  - `dmesg` **无 OOM kill 记录** → 进程不是被杀，是卡住；
  - `config-health.json`(16:13)、`delivery-queue/`(16:16)、`openclaw.json.last-good`(16:11) 仍在更新 → 进程存活但无力处理；
  - 内核日志出现 `hv_balloon: Cold memory discard hypercall failed with status 1a00000005`（WSL 动态内存回收异常）；
  - WSL 于 **16:07 重启**（钦友已跑过 `wsl --shutdown`，限制确实生效）。

**修复动作**：`.wslconfig` 改为
```
[wsl2]
memory=8GB            # = 主机 15.4GB×50%，即 WSL2 默认值
networkingMode=nat
autoProxy=true

[experimental]
autoMemoryReclaim=gradual
```
移除 `processors=4`（恢复全 16 核）与 `swap=2GB`（恢复默认）。

**教训（写入长期经验）**
1. **WSL2 的 `memory` 是上限，不是预留** —— 设小不会立刻省内存，只会在高负载时掐死进程。
2. **限制 `processors` 对多线程负载（AI agent / 推理）是隐性杀手**，比内存限制更容易被忽略。
3. 给 WSL 调参的默认姿势：**CPU 不设上限**（或接近物理核数），内存留足（≥ 主机 50%），靠 `autoMemoryReclaim` 回收。

**openclaw 关键路径（本机）**
- 装在 WSL 发行版 `Ubuntu2404` 的 `/root/.openclaw`
- gateway 端口 **18789**（bind loopback，token 鉴权）；接入通道 = 飞书 WebSocket 长连接 + `openclaw-weixin` 插件
- 启用本地 embedding 模型 `embeddinggemma-300M-Q8_0`（走 hf GGUF）
- CLI 自愈：`openclaw status` / `openclaw doctor --fix`
- 注：`openclaw.json` 中飞书 appSecret、各模型 apiKey、gateway token 均为**明文**，建议后续改走 secrets 引用。

### 火山语音协议（实测，跨项目可复用）

- **WS 帧**：上行 `[0x11][mt|flags][ser|comp][0x00][sequence 4B][payload_size 4B][payload]`；
  下行多两个字段 `[event 4B][sid_len 4B][sid]`，再 `payload_size`。
- **⛔ 最贵的坑**：`event` 号（350/351/352）与"长度"量级相近，**当长度读会整帧错位**，
  错位数据仍能切成 i16 → 音频短 100 倍却听不出解码失败。解析必须按字段名逐个取、取不出就报错。
- **事件号**：350 会话建立 / 352 句子开始（音频挂它）/ 351 会话结束 / **152 才是最后一帧**（351 与 152 两帧都表示结束）。
- **服务端不回 close**：音频推完连接一直开着，不能等 stream 返回 None，只能靠事件号判完成。
- **Resource 与音色必须同版本**，且账号授权在**握手阶段**就卡：未授权的 resource_id 直接 **403**（不是业务错）；
  搭错版本是建连之后回 `55000000`。两者修改方向相反，报错文案必须分开。
- 实测可用配对：`seed-tts-2.0` + `zh_female_vv_uranus_bigtts`（还有 `zh_female_cancan_uranus_bigtts`、
  `zh_male_yuanboxiaoshu_uranus_bigtts`、`zh_female_roumeinvyou_uranus_bigtts` 等 `_uranus_bigtts` 系）。
  本账号**没有** `seed-tts-1.0` / `volc.megatts.*` 的授权（全部 403）。
- 钦友配置里的 `/plan/` 路径段（ASR `/api/v3/plan/sauc/...`、TTS `/api/v3/plan/tts/...`）**能通**，
  是真的网关路径，不要"顺手改成文档里的写法"。

## 构建缓存治理：target/ 6 天积到 54 GB（v0.33.1）

### 事实（实测，别再重复摸索）

- `src-tauri/target/` = **54 GB**：`deps` 50 GB（`.o` 22 GB / `.pdb` 6.2 GB / rlib 2.5 GB）+
  `incremental` 1.8 GB。E 盘 200 G，一度只剩 77 G 可用。
- 构成拆开看：**30 GB 是本 crate（easyop / easyop_lib）的死产物**，只有约 20 GB 是依赖缓存。
- 26128 个 `.rcgu.o` **全是本 crate 的**（`easyop.<session>.<cgu>.rcgu.o` 命名 ⇒ 增量编译产物）。
  按 mtime 分布：09-16 101 个 → 09-21 13359 个，**单日积 1.3 万个**。
- `easyop_lib-<hash>.exe` 45 个 + `.pdb` 46 个（每个 12 MB / 130 MB）—— 全是历史 fingerprint
  的残留，Cargo 永不回收。

### 根因（第一性原理）

1. **`target/` 是只增不减的**：产物按 fingerprint（rustc 版本 / feature / profile / 环境变量）
   寻址，任一项一变就换一套新文件名，**旧的那套 Cargo 故意不删**（它无法安全判断没人用）。
2. **`.rcgu.o` 的大头来自"编译被中断"**。证据：一次**干净成功**的编译跑完后，`deps/` 里
   只剩 **6 个 / 32 KB** 的 `.rcgu.o` —— rustc 链接成功后会清掉自己的中间目标文件。
   所以那 26128 个孤儿，是每次"存盘触发连环重编 / Ctrl+C / 强杀 `tauri dev`"留下的。
   ⇒ **不要再强杀正在编译的 `tauri dev`**。
3. **`crate-type = ["staticlib","cdylib","rlib"]` 是移动端模板的默认值**，桌面版权程没人用，
   但每轮编译白写约 **1.1 GB 的 `easyop_lib.lib`**（静态库合并整棵依赖树且带全部 debug 信息）。

### 处置（已落地）

- `cargo clean -p easyop` 一把删 **28807 文件 / 57.7 GiB** → target 54 G → 22 G。
  **`-p <包名>` 是关键**：只清本包，依赖缓存完整保留 ⇒ 下次只重编本 crate（2~4 分钟），
  而不是 `cargo clean` 的全编 15~20 分钟。残留的几百个孤儿再手工扫掉即可（`-p` 匹配不到
  fingerprint 已消失的残留）。
- `Cargo.toml`：`crate-type` 改为 `["rlib"]`。**已验证生效**：本轮编译后
  `easyop_lib.lib` / `libeasyop_lib.dll` 均未生成，`libeasyop_lib.rlib` 497 MB 正常。
  ⚠️ 将来 `tauri android init` / `tauri ios init` 需要把两项加回。
- 新增 `scripts/tidy-target.mjs` + `npm run cache:tidy`（`--dry` 干跑）/ `cache:purge`。
  脚本做两件事、**顺序不能反**：先 `cargo clean -p easyop`（连 fingerprint 一起删，
  否则下次编译会误判"新鲜"去链一个不存在的 rlib），再扫孤儿 `.rcgu.o` / `long-type-*.txt`。
- README「磁盘占用与定期回收」+ AGENTS.md §6/§8 已同步；版本 v0.33.1（**patch**：
  不改应用行为、配置格式与固件协议）。校验 `version:check` exit 0。

## 第二轮：执行器合并进统一「模型配置」入口（v0.34.0）

### 做了什么

钦友提了两个诉求：① 删掉 Qwen Code / 百炼 API 等执行器，只留 codex-cli / 豆包 / DSH；
② 认为"每个执行器本质上就等同于一个模型"，建议执行器配置与 API 配置合成统一的模型配置入口。

**我的评估结论（写在 `src/components/DriverEditor.tsx` 模块头，重要，别丢）**：
提议**对了一半，且这一半很重要**。
- ✅ 对 **Api 型**执行器，"一条配置 = 一个模型"完全成立 ⇒ 默认只露 4 个字段
  （显示名 / 端点 / 模型 / Key），完成判定在 Api 形态恒为 `http_stream_end`，干脆不给选项。
- ❌ 对 **Cli 型**执行器不成立。`codex-cli` 调哪个模型写在它自己的 `config.toml` 里，
  `DriverConfig.model` 对它**一直是空的、从没被读过**。CLI 的真正身份是
  "**一个会改你磁盘的自治进程**"，需要配的是命令 / 参数 / cwd / 完成判定 / 会话续接。
  拍平成同一个"模型"表单，代价不是"少几个字段"，而是**把完成判定藏起来**——
  而"任务到底做完了没有"是这套调度里唯一不能猜的东西。
- ⇒ 落地：**入口统一，字段按形态分流**。一个入口、一张列表；按 kind 只渲染相关的项；
  其余（超时/完成判定/世界门禁/env/续接）收进「高级选项」默认收起。既满足"界面更小"，
  又不把"配错就静默判错"的字段藏没。

### 关键改动

- `config.rs::default_drivers()` **7 条 → 3 条**（doubao-api / dsh / codex-cli）。
- **退役迁移**：新增 `RETIRED_DRIVER_IDS`（bailian-api / bailian-cli / qwen-code / deepseek-api），
  `PRESET_FEATURES_VERSION` 1→2，`migrate_preset_features` **改名 `migrate_presets`**
  （它现在双向：补新能力 + 删退役项），内部分出 `retire_drivers()`。

## 第四轮：写「任务台使用说明」（v0.34.1）

钦友问：任务台执行器的设计用途是什么？怎么用？和"手动开终端 + 语音键输入 + 回车"有什么区别与优势？
要求**更新使用说明相关文档**。

### 探索到的、推翻我原有理解的关键事实

**任务台有两个出口，能力完全不同（这是整篇文档的主轴）：**

| | 出口 A：按键 S1–S4 | 出口 B：页面「派发到该槽」 |
|---|---|---|
| 任务跑在哪 | 用户正在用的**终端窗口** | **后台 headless 子进程** |
| 入队/完成判定/门禁/未读/播报/续接 | ❌ 全都没有 | ✅ 全都有 |

- 出口 A = `session.rs::dispatch_to_desk`（1726 行起）→ 用**同一份 `build_args`** 拼出
  **真正会执行的命令行**（自动摘 `--json`、含续接参数）投进终端，**不回车**。
  源码注释里明确写了设计理由："后台派发虽有队列/未读/播报那一整套，但它把过程藏起来了"。
- 出口 B = `desk_dispatch_task` → `resolve_driver` → `state::dispatch_into` → `pump_slot`。
- **前端 DeskView 有两个按钮**分别对应：`派发到该槽` / `投到我正在用的窗口（可见执行）`。

### 核出来的两个"UI 在撒谎"（本版只记录，未修）

1. **`SummaryConfig` 完全未接线。** 「设置 → 任务台 → 总结与播报」的
   「总结用执行器 / 摘要字数上限 / 总结失败退回截断原文」三项，`config.rs` 有定义、
   UI 可改可存可回读，但**运行时管线零读取点**（全仓 grep 只命中定义与无关的
   `codex_probe.hit.summary`）。实际播报正文 = `spoken_body()` 抽 Agent 最后一句
   `agent_message`，末尾截 **150 字**（`MAX_SPOKEN_CHARS` 硬编码）。
2. **槽位绑定的「按能力」/「自动判定」未实现（Phase 4）。**
   `resolve_driver`（`mod.rs:579-588`）直接返回错误；`DriverRegistry::supporting()`
   存在但**只被 UI 用来显示候选数**，不参与派发。

### 其他关键事实（都写进文档了）

- `DEFAULT_TIMEOUT_MS = 180_000`（3 分钟），照 HTTP 调用定的 → 拿它卡 CLI Agent
  会让**每个真实任务都在 3 分钟处判超时**。CLI 型预置给的是 900_000（15 分钟）。
- 完成信号四档：`HttpStreamEnd`/`LogPattern` → High；`ProcessExitZero`/`AsyncTaskPoll` → Medium
  （`AsyncTaskPoll` 未实现）；**填了 `evidence_cmd` 就升 High**。
- 世界门禁 `apply_evidence_gate`（`driver/mod.rs:485-562`）：只在基础执行已 Completed 时才跑；
  未通过会把 `Completed` **翻成** `Failed`。
- 同槽串行、跨槽并行；`MAX_DEPTH_PER_SLOT = 8`，到顶**明确报错**不静默丢。
- 续接靠 **argv `resume <id>`**（不是文件）；codex 从 `thread.started` 事件取 `thread_id`；
  `dsh` headless **不支持**跨调用续跑，所以没配续接。
- 「是否自动回车」由**全局**开关「设置 → 粘贴后自动回车」决定（出厂**关**，
  有单测 `submit_after_paste_defaults_to_off` 护着"提交权归用户"）。
- **预置三条各自的形态**：`doubao-api`（Api/HttpStreamEnd/启用）、
  `codex-cli`（Cli/LogPattern `turn.completed;task_complete`/900s/**有续接**/出厂未启用）、
  `dsh`（Cli/ProcessExitZero/900s/**无续接**/出厂未启用）。
- codex 命令**必须写 `codex.cmd`**：Windows `CreateProcess` 对无扩展名只补 `.exe`，
  而 npm 装的是 `codex.cmd` ⇒ 裸名 `codex` 必定起不来（与 PATHEXT 无关）。
