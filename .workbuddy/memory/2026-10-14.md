## 任务台播报三 BUG 修复（v0.42.0，钦友实机报告 → 直接开工全优化）

钦友报三 BUG：①首次下发任务同时就播"任务已完成"（实际才刚开始）；②完成后只播一小段；
③S1 播报中 S2 完成直接静默进未读。批复"直接开工，全都优化"。

### 根因与修复（一一对应，各配回归测试）

- **BUG 1 = codex_probe 误报（外部会话监工）**：`scan` 的 `primed` 首轮分支对"复活文件"
  （任务台自己 `codex exec resume` 追加写的旧 rollout，mtime 新但内容 23 天历史）从偏移 0
  整读 → 全历史 `task_complete` 被当新命中，`hits.first()` 播出最旧一条。
  修复：**首见一律按 EOF 登记、不读内容**（删 primed 字段与分支）；
  `run_probe` 增加桌面任务抑制：有槽在跑或 `last_desk_finish_ms` 10s 宽限内只消费偏移不出声。
- **BUG 2 = audio_out 保活截止单位错**：把 `total_from_pcm` 的**毫秒**当样本数套
  `micros = ms*1e6/rate`，48kHz 下时长缩 1/48 ⇒ >10.3s 音频在 `0.02×时长+10s` 被掐。
  修复：`PlaybackControl` 增加设备侧 `duration_ms()`（含重采样与声道展开），
  `keepalive_deadline(毫秒进毫秒出)`；两处调用方超时改用 `duration_ms()`，删估算函数。
  **没有也不该有播放时长设置**；真旋钮是 `summary.max_chars`（当前 252 ≈ 40s，建议 80–120）。
- **BUG 3 = NoticeGate 全局一本账 + 后到抢占**：「同类 kind 不重复播」四槽共用
  ⇒ S1 完成后 S2 同名终态被吞；且 Notice 到即抢播，终态结果被冲掉。
  修复：**两套账本**——进度类走全局账本（跃迁+最小间隔，原逻辑）；事件类（起点/终态）
  按 `(slot, kind)` 记账 + `EVENT_REPEAT_GUARD_MS=3_000`（只挡同拍双送达）。
  **终态播报排队**：`notice_queue`（cap 3，满丢最旧+计数）+ 单飞排水；
  排空且丢过则补发 `ResultsWaiting` 合并提醒。`may_start_playing`：结果可接管一切、
  进度类后到接管、终态绝不抢占。`dispatch_task` 把 `emit_notice(TaskStarted)` 移到
  `emit_state_if_changed` **之前**，消灭同拍双 notice 互抢。

## 灯语首轮真机：不是 BUG，是「灯语根本不看谁在跑」+ 一个真实设计缺口

钦友实机反馈：按 S1 灯语正常；按 S2 后**仍显示 S1 槽在执行**（灯也是 S1 亮）；
且**第 4、5 颗同时亮绿色**，与文档不符。

### 根因（读码确认，非推测）

`device_led.rs::language_for()` 的布局是：
- 像素 0–3 ← `snapshot.unread.slots[i]` 的 **pending 未读数**（分 3 档亮度）
- 像素 4 ← `snapshot.queue.running_count`（0–4 → 绿/黄/橙/紫/红）

**像素 0–3 完全不读"哪个槽 running"** —— 只读未读。所以"S2 在跑但灯显示 S1"是
必然结果：像素 0 亮**不是**"S1 在执行"，而是"S1 槽有未读"。这是**语义误读**，
不是灯语映射算错。灯语**从设计上就没有"哪个槽在执行"这个表达**。

### 第 5 颗亮绿 = 0 个槽在跑

`running_count == 0` ⇒ `RUN_COLORS[0] = (0,24,5)` 绿。钦友按下 S2 时 S1 若已完成/已空闲，
全局 running_count 就是 0 ⇒ 绿。代码注释明确写"0 运行时亮绿（待命），不是灭 ——
灭留给设备没连上"。所以"第 5 颗绿"是**正确**的，不是故障。

### 第 4 颗亮绿 = 槽 4 有未读

像素 3 = 槽 4。若槽 4 确有未读（例如 S4 跑完留了未读），亮绿是**正确**的。

### 真实缺口（两个，必须先定设计再改码）

1. **文档没写清"像素 0–3 是未读不是执行"**——`docs/任务台使用说明.md:90-92` 只说
   "第 1–4 颗 = 各槽未读"，但同一份文档第 42/176 行又写"产生未读（该槽灯亮）"，
   两处措辞叠加导致"亮着 = 在执行"的合理误读。**先补文档**。
2. **"哪个槽在执行"确实没有任何视觉表达**——这是真实功能缺口。当前设计把
   "执行中"信息**只放在第 5 颗的聚合数上**，丢失了槽位维度。若要表达，须新增映射
   （例如：running 槽用独立色/闪烁，与"未读绿"区分；`PLAYING_COLOR` 已有白
   `{18,22,22}` 但它只用于**喇叭正在播**，不用于**正在执行**）。

## 灯语 v2 语义重定义（v0.43.0，钦友拍板方案 B 并给定完整规格）

钦友直接给规格：S1–S4 对应四槽状态，**取消未读数显示**，四色区分
执行/播放/待播/空闲；待播用**三档亮度**间接表达未读（1–3 / 4–6 / ≥7）；
S5 不参与槽位状态，改为**按键按下时闪一下**。

### 关键设计决策（都写了理由注释，别后来人"优化"掉）

- **空闲不灭灯**：`IDLE_COLOR` 用极暗蓝 `(0,1,2)` 而非 `OFF`。
  理由：**全灭必须保留给"设备没连上/固件没烧/HID 没枚举"**，
  否则"四槽空闲"与"掉线"长得一模一样、无法诊断。S5 保持态同理用 `(1,1,1)`。
- **播放色由白改青**：v1 白 `(18,22,22)` 三通道全拉满、耗电大，且低亮度下
  易与"待播绿"糊在一起。改青 `(0,20,14)`，色相独立且亮度明显低于执行蓝。
- **执行选蓝**：黄/橙在 WS2812 上色相相邻，色觉障碍者几乎分不开；
  "在跑"是最高频状态，必须占一个离其他色都远的位置。
- **优先级 播放 > 执行 > 待播 > 空闲**：前两者是"当下正在发生"，必须压过
  "攒着等你处理"，否则干活时灯一直提示未读。
- **闪烁必须"当场下发"不能等心跳**：心跳 5s ≫ 闪烁 120ms，只置标志等心跳的话
  醒来时按键早超时，**闪烁永远发不出去**。`record_keypress()` 起后台线程
  当场发亮帧 → `sleep(120+60)` → 补发暗帧（不补这帧会亮到 ttl 15s 过期）。
  心跳续期**不传**闪烁标记，否则每 5 秒假闪一次。
- **闪烁存 `Instant` 不存墙钟**：系统时间被时区/NTP 校正跳变会让 120ms 变成
  常亮或永不亮。`Instant::elapsed()` 在时钟异常时返回饱和大值（非 panic），
  所以单向"超过阈值就灭"的判断天然安全。
- **闪烁刻意不进 `RuntimeSnapshot`**：那份是 `Serialize + Eq` 的对外契约，
  `Instant` 不可序列化 → 把灯效需求泄漏进公共结构是错的。改为
  `language_for(snapshot, flash: Option<&KeypressFlash>)` 独立传参。
- **`record_keypress` 放在 `handle_reserved_uuid` 所有校验之前**：
  它表达"设备收到了这一按"而非"这一按被采纳"，被拒的按键也必须有反馈。

### 结构拆分

判状态与选颜色**拆成两层纯函数**各自可测：
`slot_light_for(running, playing, pending) -> SlotLight`（新枚举，四变体）
+ `color_for(state, pending) -> Rgb` + `brightness_tier(pending) -> Option<(u32,u32)>`。
新增常量 `RUNNING/PLAYING/PENDING/IDLE_COLOR`、`BRIGHTNESS_DENOM=3`、
`BRIGHTNESS_MAX_TIER`、`KEYPRESS_FLASH_COLOR/IDLE_COLOR/KEYPRESS_FLASH_MS=120`。
删 `UNREAD_COLOR` / `UNREAD_TIER_MAX` / `RUN_COLORS[5]` / `unread_tier`。

## ⚠️⚠️ 灯语「按下无变化」真因：Windows HID 描述符缓存，板子上跑的不是新固件

钦友报：空闲全灭对了，但**其他状态灯完全不变**。写了探针真机实测，**抓实锤**。

### 决定性证据（`HidD_SetFeature` × Report ID × 长度 全矩阵）

| Report ID | 16B | 17B | 63B | 64B |
|---|---|---|---|---|
| `0x10` | ❌0x57 | ❌0x57 | ❌0x57 | **✅** |
| `0x11`~`0x16` | ❌0x57 | ❌0x57 | ❌0x57 | ❌0x57 |

- **只有 `0x10` 能下发，且只有 64 字节**。设备集合是 `col02`、Feature 支持 = true。
- 错误码语义要分清：`0x57 INVALID_PARAMETER` = 长度不在描述符声明里；
  `0x01 INVALID_FUNCTION` = 该 Report ID 在描述符里**根本不存在**。
  全部是 `0x57` ⇒ Windows 认为"这些长度都不合法"，而不是"这个 ID 不认识"。
- **结论：Windows 侧缓存的描述符里只有 `0x10` 一个 Feature Report。**
  而本仓库 HEAD 的描述符含 `0x10/0x11/0x12/0x13/0x14/0x15/0x16` 共 7 个
  （`TUD_HID_DESCRIPTOR(..., 64, 10)` 两个参数与 `git show HEAD` **完全一致**，
  已 diff 验证）。⇒ **板子上实际跑的固件 ≠ 本仓库 HEAD**，是更早的版本。

### 为什么之前"全亮蓝"也是同一件事

`0x12`（蓝）写不进去 ⇒ 固件回落 idle；`0x16` 也写不进去 ⇒ 一直全灭。
两种表现是**同一个根因在不同时机的两种显现**，不是两个 bug。上一轮我推断
"固件回退 0x12"方向对但没查到根上。

### 机制（下次直接用，别重查）

Windows HID 描述符**在设备枚举时缓存**，写 Feature Report 时按缓存校验长度/ID。
新增 Report ID 后**必须**：① 烧新固件 ② **让设备重新枚举**（拔插 USB / 电源开关
彻底断电重启 / 设备管理器禁用再启用）③ 再启动宿主。**只烧录不重插 = 不生效。**
本轮已烧录（app bin `0x190BC0`）但**未重插**，所以一直吃旧缓存。

### 探针方法（值得沉淀，下次遇到"下发没反应"直接用）

在 `transport.rs` 的 `#[cfg(test)] mod tests` 里加 `#[ignore]` 测试
（example 访问不到私有模块 `device`/`transport`）：
逐 Report ID × 逐长度调 `send_feature_report`，**用错误码差异区分
"长度不对"与"ID 不认识"**，再拿"能成功的 ID 集合"去反推设备真实描述符。
比读源码快且是硬证据。**诊断完记得 `git checkout` 还原**（本次已还原，
`transport.rs` 现无改动）。

### 结论沉淀（跨项目通用）

**「灯完全不响应」→ 先让设备重新枚举，不要先怀疑代码。**

「协议对不上」表现为 `ERROR_INVALID_PARAMETER (0x57)` 而非「找不到设备」，
