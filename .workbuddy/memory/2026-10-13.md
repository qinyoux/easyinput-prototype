## Super StartUp 中文乱码根因定位（诊断任务，未改代码）

钦友问：为什么 SS 命令面板检索出的中文名有时乱码，Everything 里检索却正常。

### 实测结论（第一性原理：数据通路不同）
1. **应用名侧干净**：扫 `AppIndex.scan()` 得 578 条，双重编码检测 0 真实乱码。
   开始菜单 lnk 走 WScript.Shell COM（Unicode BSTR）、App Paths 走 winreg、映射表走 UTF-8 → 都无损。
2. **文件搜索侧是 ANSI 管道**：`_sdk_search` 因 `tools/Everything64.dll`（1.1.0.18 老版）缺
   `Everything_IsQueryRunning` 抛异常 → 100% 降级到 `_cli_search`（es.exe 1.1.0.37）。
   es.exe 是 ANSI 控制台程序，stdout 跟随系统 ACP/OEMCP（本机实测均 936）。
3. **决定性对照实验**（同一关键词 `Ω_Δ_ß`）：
   - 文本管道 + gbk 解码 → `Ω_Δ_?_é`（**ß 丢失**）
   - `-export-csv` + `-utf8-bom` → `Ω_Δ_ß_é`（**完整保真**，BOM 已验证）
   → 证明 es.exe 文本模式在写 stdout 时就按 ACP 降级了，非 Python 解码侧问题。
4. **为什么"有时候"**：纯中文（CJK 在 GBK 内）无损；只有 GBK 无法表示的字符
   （ß/é/Ω/Δ/emoji/生僻字扩展B区）才出现替换符 `?` 或 `errors="replace"` 产生的 `�`。
   Everything GUI 走 SDK/内部 UTF-16，永远正确 → 形成对照错觉。

### 已验证的修复方向（未实施，等钦友定夺）
- 首选：升级 `tools/Everything64.dll` 到 1.1.0.37 对应版本，恢复 SDK 快路径（顺带解决 <5ms 目标落空）。
- 兜底：`_cli_search` 改走 `-export-csv <tmp>` + `-utf8-bom`，按 `utf-8-sig` 读，彻底摆脱 ACP 依赖。
- 注意 `-timeout` 是有效参数（es.exe -help 确认），但文本管道模式无编码开关。

- 探针目录 `.probe/` 与临时 CSV 已清理，未改动任何项目代码。
- 未完成项：SDK dll 升级、CSV 兜底实现、回归测试均**未做**。

## 修复 easyop everything.rs 中文乱码（v0.41.7，已完成）

### 钦友的疑问（值得记住的知识点）
「easyop 和 everything sdk/cli 是调用关系，为什么会解 GBK 字节？」
→ **es.exe 不是 SDK，是 ANSI 命令行程序。** 它把 UTF-16 文件名按系统 ACP（本机 936=GBK）转换后写 stdout。
Windows 管道是**裸字节流，没有编码协商机制**——子进程不会因为父进程想要 UTF-8 就改编码。
所以「调用关系」不等于「编码一致」：跨进程只有字节，没有编码契约。
另外确认：**easyop 全仓 0 处引用 Everything SDK**（无 libloading/LoadLibrary/Cargo 依赖），只用 CLI。

### 实测证据链
- 「文档」UTF-8 应为 `e69687e6a1a3`，es.exe 实际输出 `cec4b5b5`（GBK）。
- `from_utf8_lossy` 把 4 个 GBK 字节各变 1 个 U+FFFD → `�ĵ�`，**不可恢复**。
- `-export-csv <file> -utf8-bom` 首字节 `efbbbf`，严格 UTF-8 解码通过。
- 关键认知：**`from_utf8_lossy` 的「lossy」只保证不 panic，不代表解码正确**——这是该 bug 长期未被发现的原因。
- `-csv` 单独使用**不会**让 stdout 变 UTF-8（参数名有误导性）。

### 改动内容
- `es.exe query -n N -export-csv <tmp> -utf8-bom -size -attributes`，读文件剥BOM 后 `String::from_utf8`（严格，失败显式报错）。
- 临时文件名带 `pid + AtomicU64 序号`防并发覆盖；成功/失败/启动失败三路径均清理。
- 文件头错误注释「CSV 格式（UTF-8）」已改正，并写清为什么不能用 stdout。
- 新增 5 个测试（含 `test_gbk_bytes_would_break_utf8_lossy` 反向锁定，防止有人改回去）。

### 验证与踩坑

  与 `plugin_registry.rs`（PluginManifest 加 hidden 后测试构造器未跟上）是**其他 agent 的半成品**。

| 场景 | 延迟 |

### 两种模式的核心差异（第一性原理）
- **CLI**：跨进程 = 裸字节流 + 无编码协商 + 每次付 172ms 进程税。ANSI 程序，stdout 按 ACP(936) 降级。
- **SDK**：进程内调用，UTF-16 原生（仅限 **W 后缀接口**）。
- ⚠️ **SDK 的 ANSI/Unicode 双接口陷阱**：`Everything_SetSearch` / `Everything_GetResultFullPathName`
  是 ANSI 版，照样按 ACP 截断；必须用 `Everything_SetSearchW` / `Everything_GetResultFullPathNameW`。
  用错接口，编码问题和 CLI 一模一样。
- ⚠️ **DLL 版本地狱实例**：easyop 的 `tools/Everything64.dll` 是 1.1.0.18，缺
  `Everything_IsQueryRunning` → SDK 路径 fail-closed 静默降级到 CLI，「<5ms 首选」从未生效。
- 共同前提：两者都需 Everything.exe 后台运行（SDK 经 WM_COPYDATA IPC 连它），此点上无差别。

## v0.41.8 — 语音转写「说话人切换时末尾文本丢失」修复

**缺陷**：多人对话/会议中，speaker1 未定稿时 speaker2 插话或紧接接话，speaker1 末尾文本被清除/覆盖。

**三条根因**
1. `utterance_id` 本地自增计数器**只在 definite 时前进** → 打断时计数器不前进 → speaker2 帧打到 speaker1 行上，
   前端 `onPartial` 覆盖式写入 → 末尾被抹。旧代码无任何本地封口机制。
2. 跨句去重 `text != last_final` 误杀「好的/对/OK」这类连续短句 → 定稿被吞 + 计数器不前进。
3. 迟到修订（SSD 二遍 `enable_nonstream`）按新句处理 → 盖到别人正在写的行。

**方案**：`asr.rs` 新增 `UtteranceTracker` 状态机 —— 句子身份用服务端 `start_ms`；换人/换句立即封口
（`FinalReason::SpeakerSwitch`/`Boundary`）；`finalized` 表把迟到帧路由为 `UttAction::Correction`
→ 新事件 `lt-correction` → `live_translate.rs::apply_correction` 只改 `original` 不重翻译；
`flush()` 收尾兜底不丢尾巴。前端加 `finalized` 防御（已定稿行拒收 partial、不改 speaker 标签）。

**踩坑**
- 修复中实测发现同句判据只看 `start_ms` 相同 = **漏掉打断场景**（服务端把两人塞进同一条 utterance），
  必须「起点相同 **且** 说话人相同」。这是单测逼出来的，推理时没意识到。
- `cargo check` **不编译 `#[cfg(test)]`** → 前序给 `PluginManifest` 加 `hidden`、给 `RecordedSentence` 加
  `start_ms/end_ms` 时留下 4 处测试构造体缺字段，`cargo test` 直接编译失败。新增结构体字段后
  **必须跑 `cargo test`**，不能只 `cargo check`。
- Python 批量插字段时按 `endswith("PluginManifest {")` 匹配会误伤 `struct` 定义行与 `-> PluginManifest {`
  函数签名行 → 断言拦住（4≠3），加 `"struct" not in ln and "fn " not in ln` 后解决。

**验证**：`cargo test --lib` 501 passed / 0 failed（新增 9 个跟踪器测试）；`tsc --noEmit` exit 0；

## 追加：v0.41.13 「播报哪几类」文字看不清 —— 特异度覆盖，不是配色错

**钦友截图反馈**：设置 → 总结与播报 →「播报哪几类」四个标签，背景与字体几乎同色。

### 根因：不是配色选错，是**样式打架**

那四项是 `<label class="desk-prefer-item">`，外层套着 `.field`：

    .desk-prefer-item { color: var(--on-hi) }      ← 声明正确，特异度 0,1,0
    .field label      { color: var(--text-dim) }   ← 实际赢，特异度 0,1,1

`.field label` 还带 `display: block` 与 `margin-bottom`，一并压制。
**组件自己声明的颜色根本没生效**。修法：精细规则加祖先前缀
`.field .desk-prefer-item`（0,2,0）→ 0,2,0 > 0,1,1。

### 实测证据（CDP 读 getComputedStyle，非推断）

| 主题 | color | bg | 对比度 |
|---|---|---|---|
| light | `rgb(255,255,255)` | `rgb(194,65,12)` | 5.18:1 |
| dark | `rgb(26,18,6)` | `rgb(255,107,53)` | 6.54:1 |

`display` 亦确认 `block → flex`，佐证覆盖关系成立。

## 任务台播报三 BUG 根因定位（诊断任务，未改代码，日志实锤）

钦友报三个现象：(1) 第一次下发任务同时就播「任务已完成」但任务才刚开始；(2) 完成后只播一小段不播完文本，问有没有播放时长设置；(3) S1 完成在播时 S2 完成，S2 直接进未读没声音。证据源：`%APPDATA%\com.easyop.app\logs\easyop-2026-10-13.log` 23:46–23:53 时间窗 + `~/.codex/sessions` rollout 文件 + 源码。**三个都是真 bug，根因互不相同。**

### BUG 1：外部会话监工把「任务台自己的 codex 任务」误报成外部完成
机制链（四步，全部有实锤）：
1. `codex_probe` 只监控 mtime 在 24h 窗口内的 rollout；`seen` 表对窗口外条目 `retain` 回收（`codex_probe.rs:118-119`）。
2. S1 绑 codex-cli 且带 `resume <thread>` 续接 —— 任务台每次派发都追加写一个 23 天前的旧 rollout（`rollout-2026-09-20T23-28-02-01a0bf6e...jsonl`），使其重新入窗。
3. 文件不在 `seen` ⇒ 按「全新文件」从**偏移 0 整读**（`scan` 的 `None => primed => read_since(path, 0)` 分支）⇒ 全历史 18 个 `task_complete` 全成新 hit（日志：`外部会话：本次扫到 18 个完成`）。
4. `run_probe` 取 `hits.first()` = **最旧**那条（2026-09-20 的「你想查哪个城市或地区的天气？」）⇒ 任务下发后 1.8s 播「任务已完成」，真实任务还要跑 21.6s。当天 14:25 还有一次同型误报（ART-Pi 文件）。
修复方向：a) 任务台自己在跑 codex（+完成宽限 10s）时 probe 停播；b) 窗口外复活文件首见按 EOF 登记不从 0 读（符合模块「漏掉远比误报好」哲学）；c) 可选按 turn_id 去重。

### BUG 2：音频保活截止时间单位错误，>10.3s 的播报全被掐断
`audio_out.rs:195-199`：`Duration::from_micros(total_from_pcm(..) * 1e6 / rate)`，但 `total_from_pcm` 返回**毫秒**却被当样本数 —— 48kHz 下音频时长缩成 1/48，保活线程在 `0.02×时长 + 10s` 就 drop 流。实锤：88 字→13.2s 音频播到 10.5s 断（78%）；219 字→35s 音频播到 10.96s 断（31%）；≤7s 的全部完整。**没有也不该有「播放时长设置」** —— 控制念多长的真旋钮是 `summary.max_chars`（当前 252 字 ≈ 40s；该音色 ~6.6 字/s，建议 80–120）。修复 = 改 `Duration::from_millis(total_from_pcm(..))`；同函数 `speak_notice` 的等待超时 `total_samples*1000/48_000` 没除声道数（宽裕 2 倍，一并修）。

### BUG 3：终态播报去抖账本全局一本，S2 完成被 S1 同名吞掉
`NoticeGate` 规则「与上一条相同 kind 一律沉默」是 **Slot gate 四槽共用一本账** ⇒ S1 完成（last_kind=Completed）后 S2 完成同 kind 被吞：日志实锤 23:51:06.941 S2 完成**无任何播报行、无 TTS 请求**，只有未读+1，用户 23:53:02 手动按「播报未读」才听到。即使放行，`take_channel` 后到抢占也会剪断 S1 长结果；若 S1 播的是结果租约，`may_start_playing` 直接丢弃 Notice（设计如此）。人性化方案（推荐组合）：① 终态去抖改按 (slot, kind)（进度类仍全局）；② 终态 Notice 排队不抢占（上限 2–3 条丢最旧记日志），被结果租约占用时结果播完后补一条合并短通知（「又有 N 条新结果」）；③ 配合 BUG2 控单条时长。

### 附带发现（同家族）：每次派发双重播报互抢
`dispatch_task` 同拍触发「正在推进」（`emit_progress_notice` 进度扫描，elapsed≈0 也返回 Progressing）+「任务已开始」（事件）两条 notice 抢占单通道，日志里随机只播出一条（23:47:35「任务已开始」0 样本被抢；23:50:17 反被抢）。建议 TaskStarted 同拍抑制进度类，或「正在推进」设最短运行时长（如 10s）。
