# 七、Wi-Fi 链路四环节自动化（v0.37.0，14:40 起）

钦友指令：「在 WiFi 下麦克风可正常使用的前提下，优化 WiFi 这条链路：使其上电后自动监测
WiFi 环境并发起连接，无需每次手动连接；同时记录已成功连接过的 WiFi 信息，以便下次能快速
自动连接。请明确实现自动检测、自动连接、历史 WiFi 记录与快速重连的具体逻辑及触发条件。」

## 先查出来两个真 bug（之前"Wi-Fi 按钮点了没反应"的真正原因）

1. **`wifi_connect` / `wifi_disconnect` 从来没有生效过。**
   旧实现发的是 `{"cmd":"wifi_connect",…}`，而固件配置协议**没有 `cmd` 字段**、且 `schema` 必填
   ⇒ 整包被判 `InvalidSchema` **静默丢弃**；而 `send_command` 又**不等回执**就写日志"已下发"。
   ⇒ 用户看到的是"点了没反应，日志却说成功"。
2. **每次「下发到开发板」/「切换方案」都会清空板子的 Wi-Fi 端点。**
   旧载荷只有 `schema`/`target_platform`/`profiles`，而固件 `ConfigState::apply_json` 是
   **整体替换**语义（`current_ = parsed.config`，未提及字段回默认值）
   ⇒ `wifi_ssid`/`audio_host` 回空串 ⇒ 固件 `audio_ready()` 为假 ⇒ 板子主动释放 Wi-Fi。
   **这正是"键位改完，麦克风就不出声了"的根因。**

根治手段是**从类型上消灭**：删掉 `build_firmware_payload(profile)`，只留
`build_firmware_payload_with_wifi(profile, Option<WifiEndpoint>)` —— 每个调用方必须显式表态
"这次要不要带端点"，不能再默认漏掉。

## 四环节的判据与触发条件（实现见 `src-tauri/src/wifi_link.rs`）

| 环节 | 做什么 | 触发条件 |
|---|---|---|
| 自动检测 | `netsh wlan show interfaces/networks` 读「当前 SSID + 首选 IPv4 + 可见 AP」；指纹 `epoch = 当前SSID\|首选IPv4` | 1 s tick；在线 30 s / 离线 5 s 重探；USB 出现立即重探 |
| 自动连接 | 下发**带端点的完整载荷**（先 USB HID，后 UDP 直投） | T1 开机首次（3 s 宽限 + 板子未在线）· T2 USB 通道出现 · T4 离线 > 20 s |
| 历史记录 | `output_dir()/wifi_known.json`，上限 16，按成功证据排序 | 只在**离线→在线跃迁**记一次（判据 = 收到 EIHB 心跳，**不是**下发回执） |
| 快速重连 | 端点已在 NVS ⇒ **板子自己连**（固件本职，约 10 s 一轮）；上位机只做兜底 | T3 环境指纹变化 ⇒ 立即重下发；退避 0/5/15/30/60 s |

- **「连上了」的唯一可信判据是收到板子心跳**（`is_online()`，5 s 超时），不是下发成功。
- 不让板子扫环境（要改固件加 Report ID）：判据是"同网"而非"最强信号"，上位机自己读更准且**免动固件**。
- 固件**本来就会**自动重连（`preconnect_wifi("config")`）；真正缺的只是"没人把端点写进 NVS"。
- 修一个测试抓出的真 bug：`trim_known` 表满裁条目时，**刚插入的新条目证据为零、按证据排序必然垫底
  被立刻裁掉** ⇒「用户刚填的新网络自动连接永远看不到」。加 `keep` 参数豁免刚插入项。

## 下午：两个用户报障（v0.37.1）

用户报：① Wi-Fi 连接不稳定、偶尔断开；② 任务台「可接任务」显示的模型还是旧的
`seed-tts-1.0`。

### ① 心跳判据太紧 ⇒ 假离线（不是 Wi-Fi 真不稳）

**取证**（先看日志，不猜）：15:53～16:08 共 **9 次**"心跳中断 → 恢复"，成对间隔
只有 1～16 秒，且期间**没有应用重启**（最后一次启动标记是 15:12:11）：

```
15:56:55 [warn] 板子心跳中断（超过 5 秒未收到）
15:56:56 [info] 收到板子心跳，链路在线     ← 只隔 1 秒
```

**根因**：心跳周期 2 s vs 超时 5 s ⇒ 只容忍**连丢 1 个包**。实测空档 **7748 ms**
（连丢 3 个，日志里 `最近一次心跳在 7748 ms 前`）。推流 + 跑任务时抖动从 4 次涨到 9 次。

**真正的伤害是丢音**（这条最重要，一开始我只当成"显示抖动"）：
`resolve_mic` 按 `is_online()` 选录音源 ⇒ 翻转瞬间退回**电脑麦克风** ⇒
用户对着板子说话却录到静音，提示只写"空结果"。**用户说的"不稳定"是录音丢了，不是图标闪了。**

**修复三处**：超时 5 s→15 s；`now_ms()` 改单调时钟（`Instant`）；
抖动不计入 `mark_success`（`RESUMED_FLAP_MS = 30 s`）。

**时基那条值得单独记**：判据是"过了多久"，与"现在几点"无关 ⇒ 必须单调。
用墙钟时 NTP 校时会让差值跳变：往前跳 = 凭空一次离线；
**往后跳 = `saturating_sub` 归零 ⇒ 真掉线也不报**（静默失效，比误报危险）。
两处 `now_ms()` 都改成 `OnceLock<Instant>` + `saturating_add(1)`
（+1 是因为 `0` 在本仓库被当成"未开始/从未发生"的哨兵值，
业务值取到 0 会被读成"还没开始"）。

### ② 任务台显示错字段（`model` vs `resource_id`）

`DeskSnapshot.tts_model` 原先读 `cfg.tts.model` —— 而 `model` 是**百炼专用**字段，
豆包 provider 下被忽略、界面上**根本不显示**。用户界面填的是 `seed-tts-2.0`
（那个输入框叫「资源 ID」），卡片却显示陈旧的 `seed-tts-1.0`。

修法：新增 `TtsConfig::active_model()` 按 provider 分流，三处展示点统一用它
（任务台快照 / 启动日志 / `set_config` 日志 —— 启动日志里那行 `TTS 配置更新: … model=`
也是同款错）。⛔ **不能**用"哪个字段非空取哪个"兜底：切换过 provider 的配置两个字段都非空。

> **同类隐患的自查口径**：一个结构体里有"按分支才生效的字段"（provider/模式/协议分流）时，
> 任何 `cfg.xxx.field` 的**展示与日志**都可能是错的。
> 值得全局 grep 一遍 `\.field` 的用法，确认每个都经过分流函数。

### ⚠️ 验证方法上踩的坑（比 bug 本身更值得记）

因开发板不在手边（`VID_303A` 全 `Unknown`），我写了 `.workbuddy/inject_heartbeat.py`
往 UDP 17333 注入合法 EIHB 帧（20 字节，见 `ei_protocol.rs`）来驱动状态机 ——
思路本身成立，**但漏了一步核实：板子虽然 USB 不在位，Wi-Fi 那头一直在发心跳**
（日志里 `收到心跳 addr=10.x.y.z` 就是它，不是我的注入）。

后果：脚本阶段 2/3 测的全是"板子一直在线"，PASS/FAIL 都无意义。
**教训：注入式验证前，必须先确认"真信号源不在场"** —— 否则注入被真流量淹没，
而两条路刷的是同一个时间戳，连"离线"都造不出来。

**但这次误跑反而抓到一个真 bug（我的新代码引入的）**：

```
16:27:25 keyboard_audio: 收到首次心跳 addr=10.x.y.z:61598
16:27:26 Wi-Fi 链路：心跳恢复（离线 1.0 秒，判为短暂抖动，不计入成功次数）
```

**启动后的第一次连上，被判成了"抖动"**。根因：我用 `offline_ms_before == 0` 表示"首次连接"，
而 `offline_since_ms` **刻意**在"第一次评估到非在线状态"时就起表
（否则会漏掉"开机时板子本来就没连上"，T4 永不触发）⇒ 启动时板子还没发包，
第一个 tick 就把它设上了，首包到达时它已是"启动到首包的时长"而非 0。

修法：`counts_as_success(offline_ms_before, ever_online_before)` 显式传"曾经在线过"。
**"从未在线过"与"刚离线了 0 毫秒"是两件事，不能用一个数值兼任。**

> 顺带拿到一个**量化实证**：`wifi_known.json` 里 `success_count` 已经是 **14**，
> 而这张网真正只连过 **2** 次 —— 多出来的 12 次正是抖动虚增，
> 正是"抖动污染历史统计"这个 bug 的实际后果。
