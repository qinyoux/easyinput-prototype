### 踩过的坑（重要，已写进 MEMORY.md）

**用 Python 改这批 `.rs` 文件时把整个文件从 CRLF 变成了 LF**，`git diff` 瞬间变成"全文重写" ——
正是 AGENTS.md §4.6 明令禁止的"顺手格式化"。发现方式：`cmp` 报 `differ: byte 82, line 1`，
`od` 看到旧文件是 `0d 0a`、新文件是 `0a`。修法：`open(p,"rb")` → 替换字节 → 写回。
**教训：`io.open(p, encoding="utf-8")` 会把 `\r\n` 归一成 `\n`，写回即全文换行符转换。**

## 追加：那个「留给钦友用」的实例，后来**硬崩了**（12:22）

钦友说「我自己起 npm run tauri dev 失败，你帮我起软件验证一下」之后，
我留给他用的那个实例在**空闲约 1 小时 50 分**后 `abort`（不是被关掉）。日志 `/tmp/tauri-dev2.log` 末尾：

```
thread 'tokio-rt-worker' (36120) panicked at ...\alloc\src\rc.rs:3768:13:
unsafe precondition(s) violated: hint::assert_unchecked must never be called when the condition is false
thread caused non-unwinding panic. aborting.
error: process didn't exit successfully: `target\debug\easyop.exe` (exit code: 0xc0000409, STATUS_STACK_BUFFER_OVERRUN)
```

### 判定：**不是我们代码的逻辑 bug，是 Tauri 用 `unsafe` 掩盖的引用计数竞态**

`rc.rs:3768` 就是 std 的 `RcInnerPtr::inc_strong()`：

```rust
fn inc_strong(&self) {
    let strong = self.strong();
    unsafe { hint::assert_unchecked(strong != 0); }   // ← 崩在这行
```

含义**唯一**：某个 `Rc` 的强引用计数已经是 **0**，却还被 `clone()` —— 即"已经死掉的 `Rc` 又被加了一次引用"。
`Rc` 是 `!Send`（计数是非原子 `Cell<usize>`，安全前提是"永不跨线程"），
而它崩在 **tokio 1.53 的默认 worker 线程**（`tokio-rt-worker` 是 1.53 起的默认名）上 ⇒
**某个 `unsafe impl Send/Sync` 把装着 `Rc` 的类型放到了别的线程。**

### 两处实测到的病灶（都读了源码，行号可复查）

1. **`tauri::tray::TrayIcon`**（`tauri-2.11.5/src/tray/mod.rs:398-418`）

   ```rust
   pub struct TrayIcon<R: Runtime> { inner: tray_icon::TrayIcon, ... }   // inner 里是 Rc<RefCell<..>>
   impl Clone for TrayIcon { fn clone(&self) { inner: self.inner.clone(), ... } }  // ← 这里 clone 的是 Rc
   /// # Safety
   /// We make sure it always runs on the main thread.
   unsafe impl Sync for TrayIcon<R> {}
   unsafe impl Send for TrayIcon<R> {}
   ```

   触发点：`tauri/src/manager/tray.rs:48-62` 的 `tray_by_id()` 里 `Arc::unwrap_or_clone(icon)` ——
   **资源表自己持一份 `Arc`，所以强引用必然 ≥2，`unwrap_or_clone` 一定会真的去 clone `TrayIcon`**，
   于是 `Rc::clone` 每次真发生。它在 `app.rs:2618` 被托盘事件派发路径调用：
   **每一条托盘鼠标事件（Enter / Move / Leave / Click / DoubleClick）都会走一次。**

   ⚠️ **我们自己的代码正好踩在这条路上**：`lib.rs:1139` 用的是**每图标**监听器
   `.on_tray_icon_event(|tray, event| ...)`，而那个闭包**只用了 `tray.app_handle()`，根本不需要 tray**。
   （用全局 `app.on_tray_icon_event(|app, event| ...)` 就不需要 `tray_by_id`，也就没有这次 clone。）

2. **`tauri_runtime_wry::WebviewWrapper`**（`tauri-runtime-wry-2.11.4/src/lib.rs:2548,2568`）

   ```rust
   #[derive(Clone)]
   pub struct WebviewWrapper { inner: Rc<WebView>, ... }
   impl Drop for WebviewWrapper { fn drop(&mut self) { if Rc::get_mut(&mut self.inner).is_some() { ... } } }
   ```

   它住在 `WindowsStore(RefCell<BTreeMap<..>>)` 里，而 `WindowsStore` 是
   `unsafe impl Send/Sync`（注释同样是 "we ensure this type is only used on the main thread"）。
   同文件 `408` 行 `ActiveTraceSpanStore(Rc<RefCell<..>>)`、
   `1557` 行 `Box<dyn FnOnce(..) -> Result<WebviewWrapper> + Send>` 也在同一片雷区。
   隔壁 `DispatcherMainThreadContext` 里 Tauri 自己留了句注释：
   *「changing this to an Rc will cause frequent app crashes.」*（`windows` 字段用的是 `Arc`）
   —— 说明作者知道这条线，只是没清干净。

上游版本：我们锁 `2.11.5`，crates.io 上最新是 `2.11.6`（补丁级，不指望是修复）。

## v0.35.1 —— 修「取消不掉」（钦友反馈后做的）

钦友跑了一遍后反馈：**"指令下发到返回结果的延时高，而且中间无法取消执行的任务，
只能等他跑完才能停下来"**。第二个是明确要修的；第一个查下来有两个成因，只有一个是 bug。

### 症状 → 根因（实测，不是推理）

**取消信号的链路本身是完整的**：`desk_cancel_running` → `cancel_tokens[slot]` →
`run_driver` → `runner::run_stream` 每 150ms 轮询 → kill；后端终态映射
（`RunStatus::Cancelled → TaskTerminal::Cancelled`）也在。问题出在**杀掉之后收尾等不到头**：

- `Child::kill()` 只杀**直接子进程**。Windows 上 `codex.cmd` 的真实结构是
  `cmd.exe`（Rust 标准库对 `.cmd`/`.bat` 自动包的一层）→ `node.exe`。
- 杀了 cmd，**node 还活着**，而且**继承着 stdout 管道的写端** ⇒ 管道永不 EOF
  ⇒ `runner.rs` 的收尾循环 `while let Some(ev) = line_rx.recv().await` **永远返回不了**。
  表现就是"取消按下去毫无反应"。
- **实测复现**（关键证据）：`cmd /c start /b ping -n 12 127.0.0.1` ——
  父进程 `exit=0` 之后，`run()` 仍被拖住 **11.14 秒**，正好等于孙进程寿命。
- **第二个独立 bug**：`api_driver.rs` 的取消参数叫 `_cancel`，**从未被读取**。
  走豆包 API 的任务按取消毫无反应。

### 改了什么

1. `runner.rs`
   - 新增 `terminate_tree()` / `kill_process_tree()`：Windows 上用
     `%SystemRoot%\System32\taskkill.exe /T /F /PID` 杀**整棵树**（绝对路径，
     免得被用户改坏的 `PATH` 搞失效）。
     ⚠️ **必须在 `child.kill()` 之前调用** —— taskkill 靠 `ParentProcessId` 链找子孙，
     父进程一死链就断了，只剩再也找不到从属关系的孤儿。
   - 收尾循环加**硬超时**（正常退出 2s / 被终止后 300ms）+ 到点记 warn。
     这是底线保证：**无论进程树有没有杀干净，`run()` 一定会返回**。
   - `CancelToken::is_cancelled()` 改 pub；新增 `pub async fn cancelled()`（80ms 轮询）。
2. `api_driver.rs`：`tokio::select!` 让 `chat_stream` 的 future 与 `cancel.cancelled()` 竞速。
   取消分支赢 ⇒ future 被 drop ⇒ reqwest 关连接 ⇒ **请求真的被中断**。
   **刻意不给 `llm_client` 加取消参数**（那会连带改动语音编辑那条链路）。
   取消时回传空 `output` —— 半截正文不该被当成任务结果留存（历史/未读/播报都会误导）。
3. `DeskView.tsx`：运行中任务卡上直接加 `×`；按下即变「取消中…」且 disabled，
   该槽 `running` 变空后由 `useEffect` 自动撤掉标记（`cancelling: number[]`）。

# v0.35.4 — TTS 双向流式（豆包 WebSocket 双向流式 V3）

## 钦友的原始诉求

> 读官方《WebSocket 双向流式 V3》文档 → 让语音合成支持双向流式（现有双向端点**跑不起来**）
> → 顺带看现有**语音识别**结构能不能优化 → **不要破坏其他功能**。

## 真正的根因（不是配置写错，是"帧形状"不同）

同一个 `…/api/v3/tts/…` 家族，**单向与双向的上行帧结构根本不是一套**：

| 方向 | 上行帧 |
|---|---|
| 单向 | `[头 4B][sequence 4B][size 4B][payload]`，头 flags=`0b0001` |
| **双向** | `[头 4B][event 4B][sid_len 4B][sid][size 4B][payload]`，头 flags=`0b0100` |

把单向帧发给双向端点：**服务器不报错、静默等**，客户端收到的就是
「10 秒 0 帧」→ 现场那行 `等待音频超时(10 秒无新帧，已收 0 帧)` 就是这么来的。
**这是本次最大的坑：错误形状没有任何错误码**，靠读文档看不出来，只能探针实测。

## 落地

- `src-tauri/src/tts.rs`：新增 `synthesize_volc_bidirection_ws`，**单向下行帧/事件表原样不动**。
  - 新类型 `FrameScope<'a> { Connection, Session(&'a str) }` —— 把"连接类事件必须带 connection_id、
    会话类事件必须带 session_id"这条规则**编码进类型**；`Session("")` 直接返回 `Err`。
  - `build_bidirection_frame(event, scope, json_payload)` 唯一出口，字节表有单测锁定。
  - `TtsConfig::is_bidirection()`：去掉 `?`/`#`、去尾 `/` 后，**最后一个路径段严格等于 `"bidirection"`**
    （所以 `bidirection-proxy`、`bidirection/stream2` 不会被误判）。
  - `ServerFrame` 加 `pub session_id: Option<String>`（连接类存 connection_id，会话类存 session_id，
    布局相同）。`parse_server_frame` 原来只跳过 id 段，现在**捕获**；单向路径行为不变。
  - 握手：`1 → 50 → 100 → 150 → 200 → 35x → 102 → 152 → 2 → 52`。
  - **文本只放 `TaskRequest`**（实测放 StartSession 也能通，但文档写的是 TaskRequest，且不会双重合成）。
  - 音频取 `mt=0b1011` 的 352；`351` 只用来读回全文；**只有 `152` 才判终止**
    （`351` 在 TTS1.0 是**逐句**触发，当终止符会早停）。
  - `FinishConnection` 失败**忽略**（已经拿到音频了，不因此判失败）。
  - 新 `(Volc, Http) if is_bidirection()` 分支 → `InvalidInput`，明确告诉用户"这个端点要 wss://"。
  - 抽了公共 `volc_ws_connect` / `bidir_send` / `bidir_recv` / `bidir_expect`，单向路径改为复用
    （实测单向的实时回归**字节级不变**）。
- 探针脚本（零依赖，留在 `scripts/`）：
  `probe_tts_bidirection.py`（权威探针，`--repro-old` 复现 0 帧）、
  `_probe_bidir_variants.py`（四种帧形状对照，证明只有带 sid 的那种过）、
  `_capture_bidir_frames.py`（抓真实 hex 喂给 Rust 单测）。

## 实测到的关键字节/事实（下次别再重测）

- 连接类帧 `StartConnection` 真身：`11 14 10 00 | 00 00 00 01 | 00 00 00 02 | 7b 7d`
  （`{}` 的 payload 是 2 字节）。
- 会话类帧 `sid_len == 0` → 服务器回 `session ID length is zero`；
  `sid` 填了但**帧里没有 sid 段** → `parse payload size failed: body too short`。
- 400 端口那个坑不适用这里，但**档位**一致：`/plan/` 前缀是硬要求，
  去掉就是 **401 `Invalid X-Api-Key`**（官方裸路径在这套 key 上就是 401）。
- 一次成功合成（单句）：16 帧、`48000 Hz`、171778 samples、3578 ms、1513 ms 墙钟。
- 单测：`tts::tests` 37 passed / 2 ignored；全量 `cargo test --lib -- --test-threads=1`
  = **418 passed / 0 failed / 4 ignored**；两个 `#[ignore]` 实时测试（双向 + 单向回归）都手动跑过且绿。

# ASR 结构审查（钦友诉求的第三项，只审未改）

## 量化

- 单次录音到 ASR 建连**平均 231 ms**（16 次采样，最大 374 ms）。
- 今日日志 **1094** 次返回，**中途空文本 0 次**。

## 三个候选优化（均未落地，按"不拿 ASR 做无验证改动"处理）

1. **`final_text` 空覆盖隐患（低风险、建议做）**：
   `asr.rs` 第 700/729/778/809 行都是 `final_text = text.clone();` **无条件赋值**，
   而空文本恰恰是**正常 `last=true` 帧**带回来的。此刻 `emit_partial` 已经有非空守卫，
   两处不对称。改法：`if !text.trim().is_empty() { final_text = text; }`。
   实测至今没触发（1094 次 0 空），属于**潜在地雷**而非现症。
2. **`result_type=chunk` + `enable_nonstream: true`（需验证）**：理论上降延迟，
   但必须先确认"最终文本仍在 `last=true` 帧里完整回来"，否则会把末尾字丢掉。
3. **跨次复用 WS 连接（省 231 ms）**：收益有限，且引入连接生命周期管理复杂度，
   与"不破坏其他功能"冲突，暂不动。
