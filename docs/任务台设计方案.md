## 0. 一句话架构

**硬件按键 / 页面按钮 → `dispatch_task`（路由先行）→ 四槽队列（同槽串行、跨槽并行）  
→ 每槽一个单飞执行泵 `pump_slot` → driver 子进程 / HTTP 流 → 完成判定（+世界门禁）  
→ 播报 / 未读 / 历史 / 产物 / 会话回写，五路各司其职。**

## 1. 第一性原理：五条事实逼出的设计

这套机制不是"参考某产品"抄的，是五条无法回避的事实逐条逼出来的。

| # | 事实（不可否定）                                           | 直接后果                        | 设计落点                                                       |
| - | -------------------------------------------------- | --------------------------- | ---------------------------------------------------------- |
| 1 | Agent 任务耗时是**分钟级**（codex 实测中位数几分钟，长的十几分钟），远超人的耐心阈值 | "守着终端看"是纯浪费；但走开又怕丢结果        | **异步队列 + 完成通知**：说完就走，跑完喊你                                  |
| 2 | `exit code = 0` 只证明**进程结束了**，不证明**事情办成了**          | 任何以"进程退出"为完成判据的系统都在撒谎       | **四档完成判定 + 世界门禁**（`evidence_cmd`），门禁不过 ⇒ 状态从"已完成"**翻转成失败** |
| 3 | 一个槽 = 一个按键 + 一颗灯 + 一条播放通道，都是**单份资源**               | 同槽并发会让"灯亮哪个、喇叭念谁、取消哪个"全部说不清 | **同槽严格串行、跨槽并行**；队列深度硬上限 8，到顶**明确报错**不静默丢                   |
| 4 | CLI Agent 每次调用默认**全新会话**，"那刚才那个呢"答不上来              | 多轮对话必须显式携带会话 id             | **会话续接三字段配置**（id 从哪行来、哪个键、怎么带回去），按槽持久化                     |
| 5 | "它产出了什么"只能从**文件系统**观测（mtime、路径、glob）               | "自动打开产物"必须有可复现的判据           | **产物发现 = 时间窗 + 可选 glob + 打开策略**（`artifact.rs`）             |

第 2 条是整套设计的地基：任务台区别于"手敲命令看返回值"的全部差别，  
都在"谁来说了算"这件事上——**上游自述完成不算数，外部证据才算数**。

## 2. 四槽模型与并发控制

### 2.1 槽位数量的真源

`SLOT_COUNT = constants::desk_slot_count()`（`config.rs:37`）——  
**由固件保留 UUID 表推导，不写死数字**。写死的后果是"表里加了第 5 个槽位，  
配置层只认 4 个"，表现为 UI 上配了、按键下发了、按下去被 `normalize()` 截掉——  
最难查的那类 bug。当前实测值为 **4**（S1–S4）。

### 2.2 同槽串行的两层实现

| 层   | 机制                                                                         | 位置                                     |
| --- | -------------------------------------------------------------------------- | -------------------------------------- |
| 数据层 | `TaskQueue::start_next` 在 `running.is_some()` 时一律返回 `Busy`——**同槽串行的守门人**   | `queue.rs:254-275`                     |
| 调度层 | `pumping: Vec<AtomicBool>` 每槽单飞票据，`compare_exchange` 保证同时只有一个泵；泵本身是串行 loop | `mod.rs:109-115, 1915-1920, 1937-1939` |

两层都要：只有数据层守门，重复派发会起多个泵同时认领同一条；  
只有调度层票据，任务状态与执行仍然可能错位。

### 2.3 并发控制的全局形状

- **一把 `Mutex<DeskRuntime>`** 同时护住队列 + 未读账本（`mod.rs:107-108`）——  
  两个账本必须在同一次临界区里一起改，否则会出现"任务完成了但未读没记"的窗口。  
  调用方**不得跨 await 持锁**。
- 每槽 `AtomicBool` 单飞票据；`cancel_tokens: Mutex<Vec<Option<CancelToken>>>`。
- **无信号量、无线程池**：泵是 `tauri::async_runtime::spawn` 的 async 任务；  
  另有一个 `std::thread` 心跳线程做灯语续期 + 外部会话监工  
  （刻意不用 async，避免给 tokio 开 time feature，`mod.rs:2951-2970`）。

### 2.4 队列语义

- **FIFO，无优先级**（`queue.rs:246`）。任务号全局单调递增、从 1 开始（0 保留）。
- **去重只看 pending**：同 prompt ∧ 同 driver 的待执行任务 → `DuplicatePending` 报错；  
  running 中同文本**允许**（语义是"再跑一轮"，`queue.rs:197-230`）。
- **上限**：每槽 pending ≤ 8（`MAX_DEPTH_PER_SLOT`，`queue.rs:27-32`），  
  到顶返回 `QueueFull` **明确报错，不静默丢弃**。
- **跨槽并行**：每槽独立 spawn；测试 `four_slots_run_in_parallel` /  
  `one_busy_slot_does_not_block_others`（`queue.rs:486-518`）。
- **队列刻意不持久化**：重启后运行中的子进程已消失，恢复只会得到幽灵任务  
  （`state.rs:216-230`）。重启后"未读还在、队列清零"是**正确行为**，不是丢数据。

## 3. `pump_slot` 执行顺序（改编排前必读）

泵是 `loop`，**同槽串行即这个循环的形状**（`mod.rs:1937-1940`）。  
每轮顺序如下，**步与步之间有依赖，不能随意调换**：

| 步         | 内容                                                                                                                                          | 关键约束                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 0 防御      | `last_done` 记录上一个处理过的任务号，认领到已处理号立即停机报错                                                                                                      | 防迟到回执造成重复处理（`mod.rs:1948, 1981-1989`）                                                       |
| 1 认领      | `state::claim_current`。注意：`dispatch_into` 已把任务放进运行位，`start_next` 返回 `Busy`，而 **`Busy` 的真实含义是"该执行的就是这一条"**——`claim_current` 绝不把 Busy 当"队列空了" | 这个缺陷曾导致任务永久停在"正在执行"（`state.rs:293-307`）                                                     |
| 2 取配置+令牌  | 取 driver 配置、取续接会话（driver_id 不符自动作废）、登记 `CancelToken`                                                                                        | 令牌必须每条任务一登记一注销（`mod.rs:1993-2029`）                                                          |
| 3 执行      | `run_driver`，进度出口为 `NullSink`（过程输出当前被丢弃，见 §12）                                                                                              | `started_ms` 必须取在 `run_driver` **之前**——它是产物发现的时间窗起点（`mod.rs:2031-2036`）                     |
| 4 注销令牌    | 无论成败清空 `cancel_tokens[slot]`                                                                                                                | 否则取消会打到下一条任务（`mod.rs:2064-2071`）                                                            |
| 5 收终态     | `RunStatus → TaskTerminal` 映射；`complete_task` 同时改队列计数与未读账本                                                                                  | Completed→Succeeded、Failed→Failed、TimedOut→TimedOut、Cancelled→Cancelled（`mod.rs:2073-2115`） |
| 5.5 播报    | 组成本地正文（`spoken_head` + `spoken_body` 按 `max_chars` 截断）；`summary.driver_id` 空 ⇒ 直接念本地正文，非空 ⇒ 走二次总结（只喂输出尾部 8000 字）；终态 notice **早于**历史落盘       | 播报早于历史 = 前端先听到、后看到（`mod.rs:2117-2173`）                                                      |
| 5.6 结果留存  | 非 Cancelled ⇒ `pending_results[slot]` 写入 `SlotResult`                                                                                       | **刻意存本地正文而非二次总结产物**——二次总结可能失败，本地正文永远在（`mod.rs:2175-2196`）                                   |
| 5.7 历史/产物 | `discover_and_open` + `record_history`                                                                                                      | stderr 目前传空串，是已知缺口（`mod.rs:2198-2239`）                                                      |
| 6 落盘+事件   | `save_unread()` + `emit_state_if_changed`                                                                                                   | 未读必须先落盘再发事件，防"事件到了、重启丢了"（`mod.rs:2241-2247`）                                                |
| 6.5 会话回写  | **只有 driver 明确交回 `session_id` 时才更新**                                                                                                        | 防把失败任务的空会话写进去（`mod.rs:2249-2257`）                                                           |

## 4. 完成判定与可信度体系

### 4.1 四档信号与固有可信度

| `CompletionKind`    | 判据                      | 固有可信度      | 形态限制                                    |
| ------------------- | ----------------------- | ---------- | --------------------------------------- |
| `http_stream_end`   | HTTP 流正常结束              | **High**   | 仅 Api 形态（Cli 选了会被 `validate_driver` 拒绝） |
| `log_pattern`       | 日志出现权威串（`;` 分隔多候选，任一命中） | **High**   | 仅 Cli 形态                                |
| `process_exit_zero` | 子进程退出码 0                | **Medium** | 仅 Cli 形态                                |
| `async_task_poll`   | 异步任务轮询                  | **Medium** | **未实现，显式拒绝**（选了永远判不出完成）                 |

（`config.rs:92-124`，`driver/mod.rs:278-371`）

### 4.2 世界门禁（`evidence_cmd`）

**"上游自称完成 + 外部证据不成立" ⇒ 翻成失败。宁可承认失败，绝不播报成功。**

- 施加点：`apply_evidence_gate`（`driver/mod.rs:487-568`），由 `run_driver` 在形态分派后  
  **统一施加**——"信号从哪来"与"要不要过门禁"正交，故不放各自 driver 里。
- **只在基础执行成功时才跑**（`cmd.is_empty() \|\| base.status != Completed` 直接返回）——  
  基础失败再跑门禁会掩盖真正的失败原因（`driver/mod.rs:492-495`）。
- 跑在**任务同一个 cwd**；Windows 走 `cmd /C`、其它 `sh -c`；超时 60s  
  （`EVIDENCE_TIMEOUT_MS`，门禁自己也是子进程）。
- **通过** ⇒ `confidence = High`，`evidence` 入档；  
  **未过** ⇒ `status = Failed`，reason 明说"上游自称已完成，但外部证据不成立"，  
  原始输出保留；且 `confidence` 仍记 **High**——"真的没做成"这个结论本身是已校验的  
  （`driver/mod.rs:548-567`）。
- `evidence_cmd` 非空 ⇒ 整体可信度直接升 High（`config.rs:163-169`）。


### 4.3 可信度在前端的落点

任务历史里 `confidence` 非 high 的记录显示「未校验」徽标，  
title 写明"完成判定没有世界门禁背书——进程结束了，不等于事情做成了"  
（`DeskView.tsx:1381-1385`）。

## 5. 取消与超时

### 5.1 超时

| 参数          | 值                                    | 说明                                                                |
| ----------- | ------------------------------------ | ----------------------------------------------------------------- |
| 全局默认        | `DEFAULT_TIMEOUT_MS = 180_000`（3 分钟） | 照"一次 HTTP 调用"定的                                                   |
| 门禁超时        | `EVIDENCE_TIMEOUT_MS = 60_000`       |                                                                   |
| 每 driver 可配 | `timeout_ms`，**0 = 用默认**             | 预置 `dsh` / `codex-cli` 均为 900_000（15 分钟）——出厂 180 秒会把每个 CLI 任务都判超时 |
| 语义边界        | **没有"不超时"这一档**                       | 卡死的执行器会永久占住槽位，后续派发全部 Busy（`config.rs:260-264`）                    |

API 形态取 `min(请求超时, driver 折算秒)`（`api_driver.rs:159-182`）；  
CLI 形态直接进 `RunnerOptions.timeout`（`cli_driver.rs:206`）；  
runner 主循环每 150ms 轮询取消，超时到点立即 kill（`runner.rs:193-194, 308-318`）。

### 5.2 取消：先杀树，再回收

**入口** `desk_cancel_running(slot)`：取令牌 `cancel()`，无在跑任务返回 `false`（如实说，不是错误）；  
**不主动发状态事件**，等执行泵收尾时自己发（`mod.rs:3136-3149`）。

CLI 终止顺序是**硬性**的（`runner.rs:448-462`）：

1. **先杀整棵进程树**（Windows：`taskkill /T /F /PID`）——不能只 `child.kill()`，  
   `.cmd` 包出来的 node 会活着攥着管道；
2. 再 `child.kill()` 兜底；
3. **kill 后必须 `wait` 一次回收句柄**；
4. 收尾 drain 带硬超时（`DRAIN_GRACE_KILLED` / `DRAIN_GRACE_NORMAL`）——  
   防孙进程持管道导致永不 EOF。

反过来做的后果：`taskkill /T` 找不到子孙，树杀不干净。

### 5.3 取消的终态效应（三条一起构成"取消是干净的"）

- 不产生未读（`TaskTerminal::Cancelled.produces_unread() == false`，`state.rs:327-329`）；
- 不播报（`terminal_notice(Cancelled) == None`，`mod.rs:2388`）；
- 不留结果文本（`mod.rs:2182`）。

取消只影响任务本身：总结器用**独立** `CancelToken`（`mod.rs:2521`）——  
取消任务不该把"总结上一轮结果"也一起毙了。

## 7. 产物发现

判据只有一句话：**任务开始后，在工作目录里新出现的文件**。

| 规则        | 值                                                                                                                                                                | 理由                                                                       |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 时间窗       | `mtime >= since_ms`（`since_ms` = 任务开始时刻，取在 `run_driver` 之前）                                                                                                      | 不用"进程当前目录"猜                                                              |
| cwd 未配    | **不扫盘**                                                                                                                                                          | 没配工作目录就没有扫描范围，不拿进程目录猜（`artifact.rs:156-158`）                             |
| 深度 / 条目上限 | 深度 4、条目 4000，超限如实报告 `truncated`                                                                                                                                  | 可观测的收手，不是静默截断                                                            |
| 跳过名单      | 17 个目录名（大小写不敏感）：node_modules/.git/.svn/.hg/target/.venv/venv/**pycache**/.next/.nuxt/.cache/.idea/.vscode/$recycle.bin/system volume information/windows/appdata | **刻意不含 dist/build/out**——大量工具把成果写进 `out/`，排除的代价是静默的（`artifact.rs:42-73`） |
| glob 语义   | 相对 root 匹配；`*` 不跨 `/`，`**` 跨层，`?` 单字符；带记忆化回溯防指数爆炸                                                                                                                | `artifact.rs:252-317`                                                    |
| 打开策略      | 1 个产物 ⇒ 直接开；多个 ⇒ 开所在文件夹**选中最新**                                                                                                                                  | `OpenOutcome::{File, Folder}`，`artifact.rs:197-231`                      |
| 可复现性      | mtime 并列时按路径升序兜底（Windows 时间戳粒度约 1ms）                                                                                                                             | `artifact.rs:178-191`                                                    |

符号链接不跟进、隐藏文件跳过。

## 8. 未读账本与播放租约

**这是"灯亮了按下去有东西听"的全部机制。**

### 8.1 三条硬属性

1. **跨进程重启存活**（独立文件 `agent_desk_unread.json`，与配置同目录）；
2. **只能被"完整听完"消费**——`completed_fully = is_finished() && !stop_requested()`，  
   被中断的播放永远不算播完（`audio_out.rs:77-83`）；
3. **一次播放只消费一条**。

### 8.2 账本结构

- 每槽 `pending` 计数，**上限 9**（到顶不再增，generation 继续累加）；
- `Lease { slot, token, granted_at_ms, generation, granted_pending }`，  
  **token 全局单调递增永不复用**——这是"迟到回执被识破"的唯一机制；
- `LEASE_TTL_MS = 300_000`（5 分钟，TTS 150 秒上限 + 余量），`grant` 前先 `expire`；
- **持久化刻意不含租约**：重启后 `active` 为空 ⇒ 未读原封不动，  
  "播到一半拔电 ⇒ 未读保留"自动成立（`unread.rs:409-425`）。

### 8.3 两个命令，语义不可混用

| 命令                               | 语义              | 行为                                            |
| -------------------------------- | --------------- | --------------------------------------------- |
| `desk_ack_playback(slot, token)` | **"听完并递减"**     | token 精确匹配才消费一条；迟到 token 一律拒绝且不消费任何未读         |
| `desk_discard_unread(slot?)`     | **"用户主动放弃并清零"** | 该槽未读直接归零、连带作废该槽租约；记 warn 级日志（数据销毁）；必须落盘否则重启复活 |

配套 `desk_grant_playback`（ChannelBusy **不自动抢占**）/  
`desk_release_playback`（归还不消费，`release ≠ consume`）。

**铁律：任何自动流程不得丢弃未读**——只有用户显式走 `discard` 这条路。

## 9. 状态播报（Notice）

**Notice 与 Result 必须分开**：状态播报不产生未读（可丢弃、可被抢占），  
只有"终态 + 产物已交付"才产生未读。不分开的话，用户看到未读灯亮、  
按下去只听到一句"正在推进"，灯立刻失去可信度。

### 9.1 语料闭集（12 类，顺序即契约）

`code()` 同时是缓存文件名的一部分 ⇒ **新种类只能末尾追加**，  
插中间会把磁盘缓存整体错位（读到另一句音频，而且不报错）。

| code    | kind                                                   | 分组                   |
| ------- | ------------------------------------------------------ | -------------------- |
| 0       | task_started                                           | 起点                   |
| 1       | progressing                                            | 进度                   |
| 2/3/10  | running_1min / running_5min / running_15min            | 进度（档位闭集 = 3 档）       |
| 4       | completed                                              | 完成                   |
| 5       | completed_artifact_failed                              | 完成（刻意与 completed 分开） |
| 6/7/8/9 | failed / needs_confirmation / timed_out / lost_contact | 异常                   |
| 11      | results_waiting                                        | 完成（合并提醒，**非终态**）     |

（`notice.rs`；11 = 合并提醒，v0.42.0 新增：排队溢出丢最旧后补一句"还有 N 条结果未播报"）

### 9.2 去抖规则（`NoticeGate`，两套账本）

1. **分类开关**：关掉的组不记账；
2. **进度类走全局账本**：跃迁才播（同 kind 沉默，且不刷新时间戳）+ 最小间隔；
3. **事件类（起点 / 终态）按 `(槽位, kind)` 记账**：同一槽同一 kind 3 秒内重复送达才沉默。  
   ⚠️ 旧版事件类与进度类共用全局 `last_kind`，"S1 完成"会吞掉"S2 完成"  
   （v0.41.15 实锤：S2 连播报行都没有，只有未读 +1）—— 四槽并行时每槽的终态  
   都必须能分别说出来。被拦下的进度跃迁**不更新 last_kind**，下次轮询重试。

终态播报另有**排队**机制（`notice_queue`）：喇叭被占用时不抢占、不丢弃，  
排队（上限 3 条）等当前播放结束补播；溢出丢最旧并计数，排空后补合并提醒。

两本独立账本：`notice_gate`（任务台）与 `probe_gate`（外部会话监工）——  
**不能共用**，否则一条真实完成会被吞（`mod.rs` DeskManager 字段区）。

### 9.3 离线预合成缓存

- 落点 `output_dir/notice_assets/`，命名 `notice_{code:02}_{slug}.wav`；
- 有效性判据是**长度 ≥ 46 字节**（44 字节 WAV 头 + 至少 1 采样点），  
  不是"文件存在"——防中断写入的 0 字节残骸被当成可用缓存；
- 先写 `.tmp` 再 rename 原子落盘；
- `all_cached()` 是"离线播报可用"的**唯一判据**。

### 9.4 喇叭抢占门禁

`may_start_playing`：**结果在播时 Notice 一律丢弃；结果可接管任何东西**；  
`take_channel` 抢占并停掉前一个（`mod.rs:990-1026`）。

## 10. 音频输出

播放在**后端**做而非前端：「听完才消费未读」的判定点不能活在 webview 里——  
刷页面/渲染进程崩溃都会断承诺（`audio_out.rs:3-18`）。

| 项    | 事实                                                                                |
| ---- | --------------------------------------------------------------------------------- |
| 线程   | 专用线程 `easyop-desk-audio`，建流结果经 channel 回传，`recv_timeout(5s)`                      |
| 完成凭据 | `completed_fully()` = 消费未读的**唯一**凭据；被中断立刻静音 + 置 finished + **不推进游标**（"播了多少"不能变假账） |
| 硬上限  | `PLAYBACK_HARD_LIMIT_MARGIN = 10s`——设备拔掉时声卡回调可能不再被调用，硬上限保证线程必退                    |
| 采样率  | 交付恒 48000（固件要求）；源不同走 `resample_linear`；单声道复制到目标声道数                                |
| 可观测  | 每次播放记录设备名 + 两侧采样率——排查"没声音"的第一手数据                                                  |


## 12. 外部会话监工（codex probe）

场景：用户**自己开终端跑 codex**，任务台不参与执行，只在完成时告诉他一声。

三个必须做对的点（`codex_probe.rs:19-27`）：

1. **首轮只登记偏移、不产事件**——否则重启 easyop 会把历史 rollout 里的  
   `task_complete` 全当"刚刚完成"连播几十句；  
   （代价：启动前 1 秒跑完的会被漏掉——**漏报远比误报好**）；
2. **偏移只推进到最后一个完整行的末尾**（半行留待下次重读）；
3. **先用字符串预筛 `"task_complete"` 再 JSON 解析**。

其他边界：只监控 24h 窗口内被写过的文件；递归 ≤ 6 层、文件 ≤ 512；  
`summary` 取 `last_agent_message` 末尾 600 字；`seen` 表按窗口回收防无限增长。  
**刻意不产生未读、不解析完整会话、不做 IO 之外的决定**  
（结果就在用户正开着的终端里，永久驻留）。

## 13. 会话续接

不同 CLI 表达"接着聊"的方式不同，但形态一致：**① 会话 id 从哪一行输出里来  
② 那行里哪个键是 id ③ 带上它时要加哪些 argv** ⇒ 三字段配置，而非 codex 专用 driver  
（`config.rs:186-212`）。

- `build_args`：续接参数**插到 `{prompt}` 之前**——  
  `codex exec --json --skip-git-repo-check resume <id> "<prompt>"`，  
  子命令必须落在全局选项之后、prompt 之前，顺序是实测定死的（`cli_driver.rs:94-133`）；
- 只认配置指定的 `id_event_type` 事件里的 `id_field`，**不"长得像 UUID 就去认"**；
- 续接疑似失效时（判据 = `Failed && output 为空`，不看错误文案）**降级为新会话重跑一次**；
- 会话按**槽位**记忆并持久化（`slot_sessions.json`），`session_for` 核对 driver_id，  
  **跨执行器自动作废**；
- 前端可"新起一轮对话"（`desk_reset_session`）。

## 14. 配置设计与迁移

### 14.1 为什么是独立的 `agent_desk.json`

easyop 既有配置集中在 `config.json`（扁平键值）。任务台配置是**嵌套结构 + 数组**  
（driver 列表、槽位绑定），塞进去要么拍平成十几个前缀键，要么把 `PersistConfig`  
改成递归结构——后者会动到所有既有配置的读写路径。  
多 agent 共树前提下**改动面就是风险面**，所以选独立文件：  
纯增量、读写自洽、删掉即回滚。

落点 `%APPDATA%\com.easyop.app\agent_desk.json`（`app_config_dir()`）。

### 14.2 三层迁移机制

| 机制                       | 作用                                                      | 方向 |
| ------------------------ | ------------------------------------------------------- | -- |
| `normalize()`            | 槽位补齐/截断到 `SLOT_COUNT`；补回缺失的预置 driver（**只按 id 补从未出现过的**） | 加  |
| `migrate_presets()`      | 世代标记 `< 2` 时执行：删退役 id **并清掉指向它的槽位绑定/优先级列表**；给预置补续接。幂等   | 删  |
| `apply_preset_patches()` | 仅当磁盘值**正好等于已知错值**时才修正                                   | 修  |

`RETIRED_DRIVER_IDS` 必须单独成表：`normalize()` 刻意不删多余条目  
（否则用户自定义被每次启动重置），从 `default_drivers()` 删一条预置，  
老用户磁盘上那份还在且**没有任何代码路径会去清它**——  
一个只有老用户能复现的 bug。删之前先看 `migrate_presets` 有没有同步清槽位绑定。

⚠️ `preset_features_version` 字段名带 `features` 是历史留名，它现在同时管"删条目"，  
**不能改名**（磁盘格式的一部分）。

### 14.3 预置三条执行器

| id           | kind | enabled | 要点                                                                                           |
| ------------ | ---- | ------- | -------------------------------------------------------------------------------------------- |
| `doubao-api` | Api  | true    | 豆包方舟端点；completion `http_stream_end`；capabilities [text, code]                                |
| `dsh`        | Cli  | false   | `--profile headless`；timeout 900s；`ProcessExitZero` 无门禁                                      |
| `codex-cli`  | Cli  | false   | `codex.cmd`（裸名 Windows 起不来）；timeout 900s；`LogPattern` = `turn.completed;task_complete`；带续接配置 |

预置**只能停用不能删除**（删除后下次启动被补回）。

### 14.4 密钥处置

所有 `api_key` 默认空串，由用户在「模型配置」填写；仓库不留真实密钥，  
不写进 prompt / 截图；`desk_snapshot` **不含密钥**。

### 16.5 灯语语义 v2（四态 + 三档亮度 + S5 按键闪）

> v0.43.0 重定义。v1 的"第 1–4 颗=未读、第 5 颗=全局运行数五色"被**实机验证为误导**：
> 用户会把"亮着"读成"在执行"，而映射根本没读"哪个槽 running"——槽位维度的执行信息
> 整个丢失，只被聚合成第 5 颗的一个数。v2 把槽位维度直接映射回灯上。

| 像素 | 状态 | 颜色 | 判据（后端纯函数，不在前端算） |
|---|---|---|---|
| 1–4 | 执行 | 蓝 `(0,12,30)` | `queue.slots[i].running.is_some()` |
| 1–4 | 播放 | 青 `(0,20,14)` | `unread.slots[i].leased` |
| 1–4 | 待播 | 绿 `(0,24,5)` × 三档 | `unread.slots[i].pending > 0` |
| 1–4 | 空闲 | **全灭** `(0,0,0)` | 以上都不成立 |
| 5 | 按键闪 | 白 `(30,30,30)` 120ms | 按下任一任务台键 |

**互斥优先级：播放 > 执行 > 待播 > 空闲。** 前两者是"当下正在发生"，
必须压过"攒着等你处理"，否则用户干活时灯一直提示未读。

几个刻意的取舍（改前先读，别"优化"掉）：

- **空闲全灭**（v0.43.1 改）：v0.43.0 曾用极暗蓝 `(0,1,2)`，理由是"全灭要留给掉线"，
  **该判断已被实机证伪**：① WS2812 在 0–30 量级下 `(0,1,2)` 实际可辨，
  会被读成"这槽有微弱状态"，与"空闲=没事"矛盾；② 掉线本就有独立判据
  （`send_feature_report` 报错 + `led_ok` 翻转 + 翻转时日志）。
  现语义收敛为：**亮 = 有状态，灭 = 没事**。S5 保持态同步全灭。
- **播放用青不用白**：白三通道拉满耗电大，且低亮度下易与"待播绿"糊在一起。
- **执行用蓝不用黄橙**：黄橙在 WS2812 上色相相邻，色觉障碍者几乎分不开。
- **三档而非 9 档线性**：`MAX_UNREAD_PER_SLOT=9`，线性分档最暗那档
  `{0,24,5}×1/9 ≈ {0,2,0}` 实际接近看不见；人眼对亮度是对数感知的。
- **闪烁必须当场下发不能等心跳**：心跳 5s ≫ 闪烁 120ms，只置标志等心跳的话
  醒来时按键早超时，**闪烁永远发不出去**。`record_keypress()` 当场发亮帧 →
  `sleep(180ms)` → 补发暗帧（不补会亮到 ttl 15s 过期）。心跳续期不传闪烁标记，
  否则每 5 秒假闪一次。
- **闪烁计时用 `Instant` 不用墙钟**：系统时间被时区/NTP 校正跳变会让 120ms
  的闪烁变成常亮或永不亮。
- **闪烁不进 `RuntimeSnapshot`**：那份是 `Serialize + Eq` 的对外契约，
  `Instant` 不可序列化。改为 `language_for(snapshot, flash)` 独立传参。

**色值量级 0–30，不是 0–255**（与固件 `led_strip_status.cpp` 既有色板一致）。
`0x16` 是逐像素通道，**语义全在宿主侧**——改灯语不需要重烧固件。

**验证状态（v0.43.2）**：✅ **实机验证通过**（2026-10-14）。四态、三档亮度、
空闲全灭、S5 按键闪在真板上均与本节设计一致。逻辑侧另有
`cargo test --lib agent_desk` **273 passed / 0 failed** 兜底。

**一个必须知道的外部约束：Windows HID 描述符缓存。** 本轮排障的核心发现 ——
灯完全不响应时，**先怀疑设备没重新枚举，而不是先怀疑代码**。实测全矩阵探测：
只有 `0x10` 能下发，`0x12`–`0x16` 全部 `ERROR_INVALID_PARAMETER (0x57)`，
而固件源码里 `0x16` 描述符一直是齐的。根因是 Windows 缓存了旧版 HID 报告描述符：
固件更新了描述符但设备没重新枚举，主机侧仍按旧描述符校验，于是
"协议对不上"表现为"参数无效"而不是"找不到设备"。

排查口诀：让设备重新枚举（关机再开机 / 拔插 USB / 设备管理器禁用再启用）→ 再看代码。
反过来做会浪费很久（本轮就是这么绕了一圈才定位到）。

错误码语义差异也值得记：`ERROR_INVALID_FUNCTION (0x01)` 是"该 Report ID
设备根本不支持"，`0x57` 是"支持但本次参数/长度不对"。全矩阵探测必须按错误码
分类读，一律当成"失败"会丢掉这两者的区别。

| ----------- | ------------------------------------------------------------------------------------------------ |
| 任务从哪进来      | 硬件键（host_action → ptt → ASR → dispatch_to_desk）或页面按钮（desk_dispatch_task），**同一条 `dispatch_task`** |
| 为什么同槽串行     | 按键/灯/喇叭都是单份资源；两层守门：`start_next` 返回 Busy + 每槽单飞泵                                                  |
| 重启后队列为什么空了  | 刻意不持久化——恢复运行中的子进程只会得到幽灵任务；未读**会**保留                                                              |
| "已完成"可信吗    | 看 confidence：High = 有门禁背书或信号权威；Medium = 只有"进程结束了"                                                |
| 门禁没过会怎样     | 状态翻 Failed，绝不播报成功；原始输出保留                                                                         |
| 取消会丢结果吗     | 不产未读、不播报、不留结果文本——取消是干净的                                                                          |
| 怎么取消        | `desk_cancel_running(slot)`：先杀整棵进程树（taskkill /T /F），再回收                                          |
| 产物怎么算       | 任务开始后、cwd 里新出现的文件（时间窗 + 可选 glob）；跳过名单不含 dist/build/out                                           |
| 未读怎么消费      | 只有**完整听完**才消费一条（`completed_fully`）；中断/抢占都不算                                                      |
| 未读能自动清零吗    | 不能。只有用户显式 `desk_discard_unread`（两段式确认），记 warn 日志                                                 |
| 状态播报会影响未读灯吗 | 不会。Notice 与 Result 是两条独立通道，这是铁律                                                                  |
| 断网能播吗       | 语料全预合成 ⇒ 能；`all_cached()` 是唯一判据                                                                  |
| 槽位能绑"能力"吗   | 类型支持，路由未实现（Phase 4），选了报错                                                                         |
| 换模型要写代码吗    | 不用。加一条 DriverConfig（端点/密钥/能力）即可，槽位绑定不动                                                           |
| 改编排顺序行吗     | 不行。`pump_slot` 步间有依赖（播报早于历史、未读先落盘再发事件），改前读注释                                                     |
