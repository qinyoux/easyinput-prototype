## 五、核验四：两处硬技术错误

### 5.1 「模块级编译期隔离」在 Rust 不存在（v3 §4.1）

v3 主张：

> `cloud/mod.rs` 顶部 `#![forbid(unsafe_code)]`；`cloud/` 内**禁止** `use std::fs / std::path / std::io / std::process`（代码审查 + clippy 保证）；效果：cloud 模块**编译期**就无法接触文件 IO，**比 Python 运行时约束更强**。

**问题**：

1. `#![forbid(unsafe_code)]` 是 **inner attribute，只能出现在 crate root 或模块文件顶部**——放 `cloud/mod.rs` 顶部**语法上合法**，但它约束的是 unsafe，**与文件 IO 无关**。
2. **Rust 没有任何 lint 能"禁止某个模块 `use std::fs`"**。clippy 确实有 `disallowed-types` / `disallowed-methods`（配置在 `clippy.toml`），但——
   - 它们是 **crate 级**配置，作用于**整个 crate**，不是按模块；
   - 且可被局部 `#[allow]` 绕过；
   - 且要装 clippy 才生效（`cargo clippy`），**不属于编译期**（`cargo build` 不跑）。
3. 因此 v3 的"编译期保证 + 比 Python 更强"**在单 crate 扁平结构下不成立**。要真做到，唯一可行路径是**拆 workspace**：新建独立 crate `easyop-cloud`，在它的 `Cargo.toml` 里不依赖任何能碰文件 IO 的东西，主 crate 依赖它。**这是"改"不是"加"**（要动 workspace 结构、重命名 crate、`easyop_lib` 的引用）。

**改造建议**：脱敏不必追求编译期隔离，**运行时收口 + 单测覆盖**已经够且成本低得多。真正有效的一步是——把脱敏放在 `LlmClient` 内部**唯一发请求的函数**里（让 `stream_edit` / `chat` / `chat_stream` 都调用它），这样"绕过"在代码结构上就无路可走。这是**结构约束**，比类型 newtype 更实在。

### 5.2 「前端不拿 Key」会破坏现有设置页（v3 §4.4）

v3 主张：「前端不直接拿 Key，改为 `test_api_key() -> bool` 校验命令」。

**实测现有前端行为**（`src/components/VoiceSettings.tsx`）：

| 行 | 行为 | 若移除 `get_api_key` 的后果 |
|---|---|---|
| `:48` | `invoke<string>("get_api_key")` 载入 ASR Key | Key 输入框**空白**，用户无法确认"是否已配过" |
| `:63` | `setLlmApiKey(cfg.api_key)` | LLM Key 同上 |
| `:112` | `invoke("set_api_key", {key})` | （不受影响） |
| `:168` | `<input type={showApiKey ? "text" : "password"}>` | 眼睛图标失去意义 |

**结论**：直接删 `get_api_key` 会**打断"改一个字符都要重敲整串"的可用性**。正确做法是**不返明文、返掩码**：

```rust
#[tauri::command]
fn get_api_key_masked() -> MaskedKey { /* { present: bool, hint: "55a6••••" } */ }
```

前端保留"留空则不改"的语义（`set_api_key` 收到空串时不覆盖）。这样既不留明文给前端，也不破坏设置页。

## 六、核验五：依赖与「零依赖」叙事

### 6.1 v3 的新增依赖需求

| v3 依赖 | 现状 | 是否要改 `Cargo.toml` |
|---|---|---|
| TTS：`windows` crate `Win32_Media_Speech` feature | 现有 18 个 feature，**无该 feature** | ✅ 要加（会重编 `windows` crate，编译时间上升） |
| 知识库：`rusqlite 0.32` | 未引入 | ✅ 要加（含 `libsqlite3-sys`，需 C 编译工具链） |
| 向量检索：`sqlite-vec` | 未引入 | ✅ 要加 **+ 运行时要带动态库 `.dll`** |
| 提示词/配置：`yaml` 解析 | 全项目**零** yaml 依赖 | ✅ 要加（`serde_yaml` 已停止维护，建议 `serde_yml` 或索性继续 JSON） |

**判定**：v3 §5.1 说 TTS「零依赖、全离线」——**"零运行时安装"成立，但"零依赖"不成立**（必须加 feature）。这与 `扩展机制规范 §七` 对原方案的修正口径完全一致：

> **「零运行时安装（装 easyop 即可用）✓ 成立；零依赖变更（不动 Cargo.toml）✗ 不成立。」**

### 6.2 sqlite-vec 的性价比问题

`sqlite-vec` 是 **C 扩展**，Tauri 打包需一并带动态库，与 canon 的"零运行时安装"承诺**直接冲突**（用户机器上少一个 dll 就退化）。而 v3 自己把它列为决策点 4，说明作者也存疑。

**本期更划算的路径**：easyop **已有 `pinyin.rs`**（全拼/简拼/单词缩写匹配）+ `ss_palette.rs` 三层评分搜索。可以直接复用：

```
新指令 → pinyin 模糊匹配 + 评分（现成）
  ├─ 命中(阈值) → 复用本地方案
  └─ 未命中 → 云端 → 写回 JSON
```

先跑通"本地优先命中"的**行为**，等真出现"检索质量不够"再上 sqlite。**避免为一个可有可无的能力付打包成本。**

## 八、可采纳的部分（不要一起否掉）

v3 里以下判断是对的，建议**保留并纳入 easyop 自身的路线**：

| 项 | 为什么该采纳 |
|---|---|
| **API Key 加密（DPAPI）+ CSP 白名单** | 这是 easyop **现在就该修**的真问题：`config.json` 明文 Key、`get_api_key` 直返、`csp: null` + `withGlobalTauri: true`——**任何插件（隐藏 webview）一行 `invoke('get_api_key')` 就能读走 Key**。canon §6.1 已实测确认此点 |
| **命令注入修复** | 方向正确（arg 形式已做，args 级校验待补） |
| **白名单 / 高危拦截** | 只要 easyop 会执行外部路径就该有，且**成本很低**（`launcher.rs` 加一个前置 `check()`） |
| **TTS 离线播报** | 方向正确（easyop 反馈目前**纯视觉**，无 TTS 即"哑巴"）——但**落点改 Core** |
| **统一异常 + 错误码** | 已被 `capability.rs` 实现，**直接复用**，别重造 |
| **星空主题作为第三档主题** | 与 `theme.ts` 的三档结构完全吻合，是 easyop 主题令牌的自然扩展 |
| **本地 VAD** | 价值成立（当前靠服务端判停），但排期应在核心能力之后 |
| **剪贴板占用优化** | 与 `clipboard_util.rs` 现状匹配，属体验打磨 |

## 九、修订建议：优先级重排

v3 的排法（P0 安全 → P1 TTS+知识库 → P2 …）在"企业交付"语境下自洽，但对 **easyop 这个底座**而言，顺序应改为**"先定收口，再写模块"**：

| 新序 | 内容 | 与 v3 的差异 |
|---|---|---|
| **A. 收口（先做，改动小）** | ① `LlmClient` 内抽出唯一 `send()`，接入脱敏 ② `launcher.rs` 加白名单 + args 元字符校验 ③ `get_api_key` 改掩码返回 ④ API Key 落盘 DPAPI 加密 | v3 的 P0 内容基本保留，但**脱敏位置与 Key 返回方式按本文修正** |
| **B. 能力化（承接插件体系）** | 把 TTS / 知识库 / 脱敏能力注册进 **Capability Core**（`eo.speak` / `eo.knowledge_*`），使插件面与桥面**自动获得** | v3 无此概念，需新增 |
| **C. 业务插件** | 闲聊、内容台等以**插件**形态实现（`plugins/` 目录），不回写宿主 | v3 把闲聊做成 `chat/` 宿主模块 |
| **D. 体验（最后）** | 星空主题 / 波形 / 剪贴板 | 与 v3 的 P4 一致 ✔ |
| **E. 分发** | 打包 / portable / 企业配置 | 与 v3 的 P5 一致；企业配置改 `enterprise.json` 合并层 |

**一句话**：v3 的**内容清单**大体可用，**模块划分与落点**需要按 easyop canon 重画一遍。

## 十、待决策点（给钦友）

| # | 问题 | 影响 |
|---|---|---|
| 1 | **easyop 是"自用"还是"对外分发/企业交付"？** | 直接决定 P0 安全边界是"现在必须做"还是"可延后"。自用场景下白名单属过度设计，但 **API Key 明文**在任何场景都是真风险 |
| 2 | **v3 是产品方案还是课程作业？** | 若是作业，v3 的 6 层架构叙事可作为"设计表达"保留（不必与 easyop 代码 1:1）；若是产品规划，必须按 canon 重画 |
| 3 | **TTS / 知识库是否纳入 Capability Core？** | 纳入 = 插件/桥免费用；不纳入 = 只有主链路能用 |
| 4 | **是否接受拆 workspace 做真隔离？** | 接受 = 可做编译期约束；不接受 = 走运行时收口 + 单测（建议） |
| 5 | **知识库一期用 sqlite 还是 pinyin+JSON？** | sqlite-vec 会带来打包与"零运行时安装"承诺的冲突 |
