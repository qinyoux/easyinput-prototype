## 一、结论速览

**方案的技术选型是对的，但上下文是错的。**

它写给的是一个**尚不存在的"企业私有化 AI 语音桌面助手"**（6 层架构：`core/orchestrator`、`tts/speaker`、  
`config/default.yaml`、P0–P5 路线图）。而宠物方案里四个关键前提，**在 easyop 里一个都不成立**：

| 方案假设                                               | easyop 现状【实测】                              | 后果                                       |
| -------------------------------------------------- | ------------------------------------------ | ---------------------------------------- |
| `orchestrator` 状态机（`core/mod.rs`）                  | **不存在**                                    | "宠物＝状态机可视化镜像"的设计基石缺失，状态映射必须重做            |
| `tts/speaker.rs` + SAPI5 音量回调（方案称"已有"）             | **完全不存在**，无任何 TTS                          | `speaking` 状态与**口型同步**（方案最亮的功能）当前做不了     |
| `config/default.yaml` / `enterprise.yaml`（P3 企业下发） | 配置是 `%APPDATA%\com.easyop.app\*.json`（5 个） | 配置集成章节作废，改写 json 范式                      |
| P0–P5 优先级（"归入 P4，P1 TTS 完成后做"）                     | 无此路线图                                      | 排序依据失效，需按 easyop 自己的 `docs/ROADMAP.md` 排 |

**裁定**：

- ✅ **可作为"技术选型参考"**（SVG 路线、浮窗复用方向正确）
- ❌ **不可作为"实施依据"**（集成点、配置、工期、状态机都要按 easyop 现状重写）
- ⚠️ 还有 **2 个方案完全没提、但决定成败的硬问题**：**点击穿透** 与 **自定义形象的注入面**

## 二、可行性逐项裁定

### 2.1 站得住的部分

| 项           | 裁定   | 依据【实测】                                                                                                                                               |
| ----------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 浮窗机制复用      | ✅ 成熟 | 已有 4 个浮窗，全部 `transparent(true)` + `always_on_top(true)` + `skip_taskbar(true)` + `decorations(false)`，且**启动时创建、常驻不销毁**（初始 `visible(false)`）          |
| 事件总线接入      | ✅ 可行 | 现成事件：`asr-state` / `asr-partial` / `asr-final` / `edit-state` / `edit-selected` / `edit-llm-chunk` / `edit-done` / `host-action` / `ss-palette-show` |
| SVG 零素材依赖   | ✅ 属实 | SVG 是文本，确可零素材产出、体积极小                                                                                                                                 |
| 位置记忆        | ✅ 可行 | 同 `profiles.json` 范式，新增 `pet.json` 即可                                                                                                                |
| 可关闭 / 降级回托盘 | ✅ 简单 | 配置项 + 启动判断                                                                                                                                           |

### 2.2 有硬缺口的部分

| # | 缺口                            | 严重度  | 说明                                                                                                                                 |
| - | ----------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **没有 TTS**                    | 🔴 高 | 方案 1.4 的三通道联动写着"通道3：SAPI5 发声（**已有**）"——easyop 里**没有**。所以"语音+表情+文本"实际只有**表情+文本两通道**；"嘴巴按音量开合"无音量数据源                                 |
| 2 | **点击穿透能力从未实现**                | 🔴 高 | 全项目 `set_ignore_cursor_events` **零使用**。桌宠若不穿透，**透明区域会吃掉鼠标事件**，用户点桌面图标/切窗口会被挡住——这是桌宠的**生死线**，方案通篇未提                                 |
| 3 | **`happy`/`sad`/`warn` 无数据源** | 🟡 中 | 这三态需要"任务执行结果"。easyop 执行完 ⌘SS 命令只收面板，**没有结果事件**；要么新增事件，要么砍掉这三态                                                                      |
| 4 | **全屏检测无方案**                   | 🟡 中 | `always_on_top` 只等于 `WS_EX_TOPMOST`，全屏游戏 / 部分播放器 / UAC 提权窗口**仍会盖住宠物**。方案说"自动隐藏"，但没说怎么判全屏（需轮询 `GetForegroundWindow` + 窗口矩形与显示器矩形比对） |
| 5 | **"下发改 SVG 字符串"是注入面**         | 🔴 高 | 方案把它当"零成本优势"，实际是**新增攻击面**——详见 §4.2                                                                                                 |

## 三、性能数字：需重估

方案 3.2 的表格给 SVG 方案"**内存 < 15MB**"。这个数字**与架构事实不符**。

**事实（机制层面）**：Tauri 的每个 `WebviewWindow` 在 Windows 上对应**一个 WebView2 实例**。  
多实例共享 runtime 与浏览器进程，但**渲染进程是各自独立的**。  
所以"多一个宠物窗口"的开销 = **一个 WebView2 渲染进程的开销**，  
而不是"一个 SVG 页面的 DOM 开销"。

**实测（现状）**：easyop 已有 **4 个常驻 webview**（启动即创建、`visible(false)`，  
所以它们虽不渲染画面，但进程与实例已在）。宠物将是**第 5 个**，  
且是**唯一默认可见、且带常驻动画**的那个。

**推断（待实测，不编数字）**：新增宠物窗口的内存增量在**数十 MB 量级**，  
明显高于方案所称 15MB。原因是那 15MB 更接近"SVG 页面自身开销"，而漏掉了进程开销。

> **实测方法**（跑一次即可定案）：  
> ① `npm run tauri dev`，记录 `msedgewebview2.exe` 的进程数与工作集合计；  
> ② 临时创建宠物窗口，再记一次；  
> ③ 差值即为真实增量。建议把这一步作为**开工前的第一个 spike**。

**另一个被方案忽略的成本——续航**：  
CPU 占用只是账面，真正疼的是**常驻动画会阻止 WebView2 进入低功耗状态**。  
笔记本上，"每 2 秒呼吸一次"和"60fps 常驻呼吸"对电池的影响完全不同。  
优化方向：`idle` 时降帧或降为静态图（可参考 CSS `animation-timing-function: steps()` 或空闲时暂停渲染）。

## 四、优化空间

### 4.1 【最重要】状态机必须重新映射到真实数据源

方案的状态机是"先画好 9 个状态，再找数据"。正确顺序反过来：  
**先列 easyop 真正能观测到的事件，再从事件推导状态。**

| 方案状态           | easyop 真实数据源【实测】                       | 裁定                                               |
| -------------- | -------------------------------------- | ------------------------------------------------ |
| `idle`         | 无活动                                    | ✅ 可做                                             |
| `listening`    | `asr-state` = 采集中                      | ✅ 可做                                             |
| `thinking`     | `asr-state` = 识别中 / `edit-state` = 编辑中 | ✅ 可做                                             |
| `speaking`     | —（**无 TTS**）                           | ⚠️ **降级**：改为"气泡正在显示"（复用 overlay 显示期），不叫 speaking |
| `happy`        | —                                      | ⚠️ 需新增"执行成功"事件                                   |
| `sad` / `warn` | —                                      | ⚠️ 需新增"执行失败 / 被拦截"事件                             |
| `sleeping`     | 本地计时器                                  | ✅ 可做                                             |
| `drag`         | 本地拖动状态                                 | ✅ 可做                                             |

**建议 v1 只做 6 态**：`idle` / `listening` / `thinking` / `bubble`（替代 speaking）/  
`sleeping` / `drag`。等"执行结果事件"补上，再加 `happy`/`sad`/`warn`。

> 原则：**每个状态都必须有真实数据源**，否则就是空壳动画——  
> 用户会很快发现"它高兴/难过跟我做的事没关系"，情感连接反而崩塌。

### 4.2 【安全】自定义形象不能注入原始 SVG 字符串

方案 1.1 与 4.4 把"企业下发改 SVG 字符串"当作核心优势。**在当前 easyop 里这是个洞**：

【实测】项目现状是 `csp: null` + `withGlobalTauri: true`，且自定义命令不进 ACL。  
这意味着 **webview 里任意一段脚本都能 `invoke('get_api_key')` 读到 API Key**。  
若再把外部传入的 SVG 字符串直接塞进 DOM（`dangerouslySetInnerHTML` 之类），  
攻击者可在 SVG 里藏 `<script>` / `onload` / `<foreignObject>` → **任意代码执行 → 读走密钥**。

**两条修法**（建议至少做第一条）：

1. **形象只作数据**：自定义形象定义为 JSON（path 数组 + 颜色 + 变换），  
   由宿主组件渲染，**永不把外部字符串当 DOM 插入**。
2. 若一定要收 SVG 字符串：**白名单净化**——只允许  
   `path`/`circle`/`rect`/`ellipse`/`polygon`/`g` 与 `fill`/`stroke`/`stroke-width`/`transform`，  
   剔除 `script`/`on*`/`foreignObject`/`use`(外链)/动画事件属性。

### 4.3 【结构】宠物是宿主一等公民，**不是插件**

第一性原理：**宠物的全部价值 = 宿主状态的可视化镜像**。  
这决定了它必须满足三件事：  
① 订阅宿主事件总线；② 常驻、不可卸载；③ 持有浮窗权限。

而插件体系（v0.7.0 刚建的）是**沙箱化、可卸载、且激活层尚未实现**的 ——  
把宠物塞进插件，等于**主动丢掉它唯一的价值来源**。

**推荐切分（干净且各得其所）**：

| 层                            | 归属                                                          | 理由                   |
| ---------------------------- | ----------------------------------------------------------- | -------------------- |
| 宠物**机制**（窗口、状态机、事件接线、位置记忆）   | **宿主**，`src-tauri/src/pet/`，与 `ss_palette` / `workbench` 同级 | 需要宿主事件与权限            |
| 宠物**形象**（角色 SVG / 配色 / 动画参数） | **插件**（`plugins/pet-skin-*/`）                               | 纯数据、可卸载、可更换，正好是插件的形态 |

这样"换装"天然就是插件能力，无需为它单独设计下发机制。

### 4.4 【成本】形象美观度被严重低估——风险压在最有卖点的地方

方案说"**助手可独立产出全部 SVG 代码**"，据此把形象绘制压到 2 人天。  
但现实是：**"能产出 SVG 代码" ≠ "能产出有情感连接的角色"**。  
手写几何 SVG 角色通常像"色块拼图"，很难撑起方案的核心卖点（陪伴感/情感连接）。

**三条路线对比**：

| 路线            | 观感       | 成本 | 体积     | 建议                               |
| ------------- | -------- | -- | ------ | -------------------------------- |
| 手写 SVG 几何     | 低（可用但偏冷） | 极低 | < 50KB | **v1 用它跑通链路**（极简：圆脸 + 眼睛 + 两点表情） |
| **生成立绘 + 抠图** | 高        | 中  | 2–5MB  | **v2 升级**                        |
| Sprite 序列帧    | 中        | 高  | 500KB+ | 不做（要逐帧素材）                        |

> ⚠️ 方案的一个**事实错误**：它说"助手无法直接产出 PNG"，据此排除位图路线。  
> 但本机**已有实测可用的生图通道**（`gpt-image-2` / 火山 Seedream 4.5、5.0），  
> 加上抠图流程，产出一组宠物立绘是可行的。这条路线不该被一句"无法产出"排除掉。

生成路线的硬约束（决定它只能做 v2）：

- **跨状态形象一致性**——同一角色 9 张图，这是生图的老大难，需固定 seed + 参考图 + 反复挑图；
- **透明底**——生成图多为白底/彩底，需抠图；
- **体积**——从 < 50KB 涨到 2–5MB，与"轻量"目标冲突。

### 4.5 【排序】不要照搬方案的"P4 末位"

方案把宠物排 P4，是"企业助手"语境（那里 P0 安全最紧）。  
但**在 easyop 里，宠物不依赖任何未实现的前置**（唯一例外是 TTS），  
且它是**唯一一个"用户每天都会看见"的功能**（⌘SS 面板只在搜索时出现）。

建议作为**独立小版本 v0.8.0** 推进：

| 步骤                | 内容                                                  | 前置       |
| ----------------- | --------------------------------------------------- | -------- |
| **Spike（先做，1 次）** | ① 量出宠物窗口的真实内存增量；② 验证"透明区点击穿透 + 宠物本体可点"能否实现          | 无        |
| ① 骨架              | `pet.html` + 窗口创建（透明/置顶/无边框/跳过任务栏）+ `pet.json` 位置记忆 | Spike 通过 |
| ② 状态              | 6 态状态机 + 订阅 `asr-state`/`edit-state` 两个事件           | ①        |
| ③ 形象              | 极简 SVG 角色 + CSS 动画（呼吸/眨眼/四态表情）                      | ②        |
| ④ 联动              | 气泡文本跟随 ASR 结果与编辑结果（复用 overlay 的内容，不重复造）             | ②        |
| ⑤ 设置              | 开关 / 尺寸 / 位置 / 隐藏                                   | ①        |

**明确不在 v0.8.0 做**：口型同步（无 TTS）、`happy`/`sad`/`warn`（无结果事件）、企业形象下发（有注入面）。

### 4.6 位置记忆与多显示器

- 位置/开关存 `%APPDATA%\com.easyop.app\pet.json`（**不是** `config/default.yaml`，easyop 无此文件）
- 多显示器：用 Tauri 的显示器 API 按"所属显示器 + 相对坐标"记忆；  
  **必须处理"显示器被拔掉后坐标落空"** → 回落到主屏右下角，否则宠物会消失在屏幕外

### 4.7 复用而非重造：气泡内容已在手边

方案 1.4 设计了气泡的逐字滚动等行为，但 easyop 的 `overlay.html` **已经在做**这件事  
（跟随语音输入做实时转写，弹出定位到光标下方）。  
建议：宠物气泡**复用同一份文本事件**（`asr-partial` / `asr-final` / `edit-llm-chunk`），  
只是渲染位置与样式不同——**不要为宠物再写一套文本流**。

## 六、待确认决策点（更新版）

1. **形象**：v1 用极简 SVG 几何，还是一步到位做生成立绘？【建议：v1 几何，v2 生成】

## 七、一句话总结

> 方案的**方向**可以采纳（SVG + 复用浮窗），但**内容**必须按 easyop 现状重写：  
> 砍掉对 orchestrator / TTS / yaml 配置的假设，补上点击穿透与形象注入面这两个致命缺口，  
> 把 9 态收敛到 6 态、让每个状态都有真实数据源，并把形象从"纯手写 SVG"改为  
> **v1 几何跑通 → v2 生成升级**的两段式。
