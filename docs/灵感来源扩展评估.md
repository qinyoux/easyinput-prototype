# 内容台灵感来源扩展评估（读多 Agent 会话）

> **版本** v1.0 · 2026-09-18 · 状态：待评审
> **评估问题**：内容台作为 easyop 组件后，"灵感收集"能否扩展到读取 Trae / Codex / Claude 等 Agent 的会话，从而扩大灵感范围？
> **方法**：所有结论基于本机实测（真实路径 + 真实解析结果）。凭推测得出的部分在第十节单独列出，未混入结论。
> **本文不含任何代码改动。**

---

## 一、结论先行

**可行。但必须先把提问的前提纠正掉。**

上一轮的表述是：

> "他和 WorkBuddy 的关系与其他 Agent 无异，现在既可以读 Trae、Codex、Claude 这种 Agent"

**这句话在本机不成立。** 实测本机 4 个 Agent 的本地落盘能力，相差三个数量级：

| Agent | 本地有对话落盘吗 | 实际能读到什么 | 证据 |
|---|---|---|---|
| **Codex** | ✅ 完整 | **提问 + 回答全文**，41 个会话 | `.codex\sessions\**\rollout-*.jsonl` |
| **WorkBuddy** | ⚠️ 仅元数据 | 只有**标题 / 时间 / 模型**（话题级） | `workbuddy.db` → `sessions` 表 |
| **Trae CN** | ⚠️ 仅提问侧 | 只有**用户输入**，回答在云端 | `state.vscdb` → `input-history` |
| **Claude** | ❌ 无 | 本机**未安装** | 无 `~/.claude` |

所以正确的问法不是"能不能读 Agent"，而是：

> **"按能读到的东西分成三层，每层的成本和收益各是多少？"**

一句话结论：**L1（产物文件）+ L2（话题）覆盖 90% 的灵感需求，成本不到 2 天；L3（全文）只有 Codex 值得做。**

## 二、实测数据（这是全篇的地基）

### 2.1 Codex —— 本机唯一"完整对话落盘"的样本

```
C:\Users\86136\.codex\
├─ sessions\2026\03\03\rollout-<时间戳>-<uuid>.jsonl   ← 完整会话，41 个
├─ session_index.jsonl                                  ← 19 条，含 thread_name（会话标题）
└─ history.jsonl                                        ← 41 条，{session_id, ts, text} 输入历史
```

`rollout-*.jsonl` 的行结构（实测）：

| 行 | `type` | 内容 |
|---|---|---|
| 0 | `session_meta` | `payload{cwd, model_provider, cli_version}` |
| 2 | `response_item` | `payload{type:"message", role:"user", content}` ← **用户提问** |
| … | `response_item` | `payload{type:"message", role:"assistant", content}` ← **助手回答** |

覆盖时间：**2026-03-03 → 2026-09-09**（41 个会话）。

`session_index.jsonl` 的 `thread_name` 直接是话题，例如实测样本：

```
"Clarify using API key for agent code"
"搭建 OpenClaw 运行环境}{"
"制作AI工具比较PPT并整理MD文档"
```

> **`thread_name` 就是"我最近在琢磨什么"——天然就是灵感条目，且已按时间排序，零解析成本。**

### 2.2 WorkBuddy —— 只有元数据，正文不落本地明文

```
C:\Users\86136\.workbuddy\workbuddy.db   (SQLite)
└─ sessions 表 (44 行)
   id / cwd / user_id / title / custom_title / status /
   created_at / updated_at / deleted_at / model / expert_id / project_id ...
```

实测 `title` 样本（这就是话题级灵感）：

```
重试并替换小红书图片生成
每日灵感采集 · 对话+资料库+情报卡
阅读飞书文章并选择作业方向
检查运行环境及项目目录大小
```

**正文不在本地明文**：`sessions` 表不含消息体，正文散在 `blobs/`（559 个文件）与服务端。`sessions/*.json` 那批文件经实测**只是进程心跳**（`pid`/`sessionId`/`lastHeartbeat`/`url`），不是对话。

### 2.3 Trae CN —— 只有"提问侧"，回答在云端

Trae 是 VSCode 系（`AppData\Roaming\Trae CN`），对话存在各工作区的 SQLite：

```
User\workspaceStorage\<hash>\state.vscdb  → ItemTable
  key = "icube-ai-agent-storage-input-history"
  value = JSON 数组，每项 {inputText, parsedQuery, multiMedia}
```

24 个工作区中，**18 个**含此键。实测 `inputText` 样本：

```
"请根据 `e:\MY_AI\Tools\folder-manager-trial\rev5\哈利文件夹管理系统_开发提示词 (1).md` 重新开发一款windows文件管理系统工具"
"我运行main.py，报错，请帮我解决"
```

而 `User\chat_sessions\` 目录**是空的**（只有一个 `migration.touch`），加上 `state.vscdb` 里的 `chatHistoryNeedToBeMigrated-*` 键——**Trae 的对话正文在云端，本地只留提问**。

> 结论：Trae 能贡献"我提过什么问题"，贡献不了"AI 回答了什么"。

### 2.4 Claude —— 本机未安装

无 `~/.claude`，无 `claude` 命令。**v1 无法纳入。**

但值得记一笔：Claude Code 的会话格式是 `~/.claude/projects/<路径编码>/*.jsonl`——**同样是 JSONL**。将来若安装，可直接复用 Codex 的解析器，增量成本接近零。

## 三、来源分三层（这决定了成本）

把所有可能的来源按"能读到什么"归成三层：

| 层 | 内容 | 覆盖 Agent | 实现手段 | 新增依赖 | 估算 |
|---|---|---|---|---|---|
| **L1 产物** | 各 Agent 写出的**文件**（md / py / docx / pptx） | **全部**（含未安装的） | 复用 `everything.rs`（es.exe） | **0** | 0.5d |
| **L2 话题** | Codex `thread_name` / WB `title` / Trae `inputText` | 3 / 4 | JSONL 直读 + SQLite 只读 | **rusqlite**（见 §6.2） | 1~1.5d |
| **L3 全文** | 完整对话（提问+回答） | **仅 Codex** | JSONL 解析 + LLM 摘要 | 0 | 1d |

**三点关键判断：**

1. **L1 被严重低估。** 灵感不需要"读过对话"，只需要"知道你在做什么"。而你在 Trae 里做的文件系统工具、在 Codex 里写的脚本、在 WorkBuddy 里产出的报告——**这些产物本身就是最实的灵感线索**，而且 `everything.rs` 已经能全盘搜。**零新依赖，覆盖全部 Agent（包括未装的）。**
2. **L2 是性价比拐点。** "我最近问过什么"比"文件叫什么名"更接近灵感，且三家格式都简单。代价是**必须引 rusqlite**（§6.2 详述）。
3. **L3 只有 Codex 值得做**，因为只有它落全文。为 WorkBuddy/Trae 补 L3 = 逆着它们的架构设计走（它们的正文在云端），**不划算，不建议**。

## 四、第二条路：不是"读历史"，而是"主动问"

上面三条都是**被动读**。还有一条正交的路——**主动调用**。

实测本机 CLI 可达性：

| CLI | 状态 | 路径 |
|---|---|---|
| `codex` | ✅ 可用 | `C:\Users\86136\AppData\Roaming\npm\codex` |
| `trae` | ✅ 可用 | `D:\Users\86136\AppData\Local\Programs\Trae CN\bin\trae` |
| `claude` | ❌ 未安装 | — |

而 easyop **已经有起进程的能力**（`launcher.rs` 的 `open_entry`）。

这条路的语义完全不同：

| | 被动读历史 | 主动调用 |
|---|---|---|
| 拿到的是 | 你**已经**想过的东西 | Agent **现在**为你想出来的东西 |
| 时效 | 取决于你多久没用过它 | 实时 |
| 成本 | 解析文件（便宜） | 起进程 + 等结果 + 超时处理（贵） |
| 失败模式 | 格式变了解析失败 | Agent 卡住/超时/要登录 |

**评估结论：主动调用不作为 v1 的主路径，但应作为 L1/L2 的"下一步动作"**——即：从 L1/L2 得到线索后，点一下"让 Codex 就这条深挖"，而不是一上来就无差别调用。

> 另有一个必须点明的边界：`launcher.rs` 现有实现是 **fire-and-forget**（拿不到输出与退出码）。要做主动调用，必须先补一个可观测执行器——**这正是《内容台集成方案.md》第八节已列出的 `runner`**。所以这条路**复用同一块基建**，不额外造轮子。

---

## 五、第三条路：复用你已经在跑的 automation（成本最低的一条）

实测 `workbuddy.db` 里，你**已经在跑**这条链：

| 项 | 实测值 |
|---|---|
| 会话标题 | 「每日灵感采集 · 对话+资料库+情报卡」 |
| 运行记录 | 09-14 / 09-15 / 09-16 / 09-17，**每天 17:30** |
| 模型 | `deepseek-v4.1-flash` |
| 工作目录 | `E:\MY_AI\output` |
| 另一条 | 「超声硬件前沿速递·月度整理」（7 方向搜索 → IMA → 公众号格式） |

这意味着：

> **"灵感采集"这件事已经有一个跑通的实现，而且它的来源已经是"对话 + 资料库 + 情报卡"。**

于是出现一条**几乎零成本**的路径：

**内容台不重写采集逻辑，只消费它的产出。** 即：

```
WorkBuddy automation（已有，每天 17:30）
   ↓ 采集 + LLM 判断"什么算灵感" + 结构化
E:\MY_AI\output\<...>   或   平台资料库表
   ↓ 内容台读取（这就是 L1：读产物文件）
内容台「灵感收集」面板
```

**收益**：直接继承"什么算灵感"的判断逻辑（这是最难的部分，且已被验证）；**成本 ≈ L1**。

**代价**：依赖 WorkBuddy 在跑。所以是**组合**而非替代：

| 场景 | 走哪条 |
|---|---|
| 每日沉淀、跨源聚合、需要 LLM 判断 | **复用 automation 产出**（§5） |
| 刚在 Codex 里聊完，想立刻拉进来 | **组件直接解析**（§3 L2/L3） |
| 想找"我写过的某个文件" | **L1 everything 搜索**（§3 L1） |

## 六、架构落点

### 6.1 扩展点：`collect.rs` 的 `InspirationSource`

《内容台集成方案.md》已定义：

```rust
// studio/collect.rs —— 原设计
pub fn collect_source(kind) -> Vec<Inspiration>
```

`kind` 原为 `对话记录 / 剪贴板 / 手动 / 本地文档目录`。**扩展只需把"对话记录"这一档细化为多个具体来源**，收口到一个 trait：

```rust
pub trait InspirationSource {
    fn id(&self) -> &'static str;              // "codex" | "workbuddy" | "trae" | "files"
    fn probe(&self) -> SourceState;            // 可用性探测（未装/版本不符/无数据）
    fn collect(&self, q: &Query) -> Result<Vec<Inspiration>, CollectError>;
}
```

**三条设计铁律**（都来自 easyop 的既有风格）：

1. **探测先行**：每个源必须能回答"我现在能不能读"。读不了就明确显示 `Trae 未安装` / `Codex 无新会话`，**绝不静默返回空数组**——这与 `everything::is_available` 同构，也是"能验证的才自动化"的落点。
2. **单源失败不影响整批**：一个源解析失败（格式漂移）只标记该源，其余照常。
3. **来源可禁用**：每个源有独立开关，配置落在 `studio.json`（与既有 JSON 数据层一致）。

### 6.2 一个必须拍板的依赖：`rusqlite`

L2 要读 WorkBuddy 与 Trae，**它们都是 SQLite**。而实测 easyop 现有依赖：

| 依赖 | 状态 |
|---|---|
| `serde_json` | ✅ 已有（解析 JSONL 够用） |
| `reqwest` / `tokio` | ✅ 已有 |
| **`rusqlite`** | ❌ **没有** |
| **`toml`** | ❌ 没有 |

三条路：

| 选项 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A. 引 `rusqlite`（bundled）** | 自编译 SQLite，无外部依赖 | 体积 +1~2MB、编译时间增加 | **推荐**——L2 的价值主要在 WorkBuddy，而它恰好是你最活跃的 Agent |
| B. 起 `sqlite3.exe` 子进程 | 零新依赖，复用 `Command` | 依赖用户机器上有 sqlite3.exe | 脆弱，不推荐 |
| C. 只做 Codex + 文件 | 零新依赖 | **放弃 WorkBuddy 与 Trae 的话题源** | 若想零依赖则可接受 |

> 注意：这与《集成方案》第六节"不引 rusqlite"**不矛盾**——那条针对的是 **studio 自己的业务台账**（几百条，用 JSON 足够）；而这里是**读别人的外部格式**，性质不同，可分开决策。

## 七、难度分级

| 来源 | 层 | 难度 | 估算 | 主要工作 |
|---|---|---|---|---|
| 各 Agent 产物文件 | L1 | ★☆☆☆☆ | 0.5d | 复用 `everything.rs`，加"来源过滤 + 按 Agent 归类" |
| Codex 话题（`thread_name`） | L2 | ★★☆☆☆ | 0.5d | 读 `session_index.jsonl`，最简单的一个源 |
| Codex 全文 | L3 | ★★★☆☆ | 1d | 解析 `rollout-*.jsonl` + 按 role 抽消息 + LLM 摘要 |
| WorkBuddy 话题（`sessions.title`） | L2 | ★★☆☆☆ | 0.5d | 引 `rusqlite` 只读；**注意只读打开，防锁库** |
| Trae 提问（`input-history`） | L2 | ★★★☆☆ | 0.5~1d | 遍历 24 个工作区 vscdb + 容错解析 |
| WorkBuddy / Trae **全文** | L3 | ★★★★★ | **不做** | 正文在云端，逆架构，不建议 |
| 主动调用 Agent CLI | — | ★★★★☆ | 2d | 需先补 `runner`（已在集成方案第八节） |

**一期总估算：L1 + L2 + Codex L3 ≈ 3 天**（不含 UI，UI 已含在既有 `InspirationPanel.tsx` 里）。

## 八、风险登记

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| 1 | **格式是未公开内部格式**，随 Agent 版本变（`state.vscdb` 键名、`rollout` 行结构都可能改） | 高 | 探测先行 + 单源失败隔离 + 容错解析（**解析不出就报"格式可能已变"，不崩**） |
| 2 | **读 SQLite 时锁库**（WorkBuddy 正在运行时） | 中 | 只读模式打开 + 短连接 + 失败即跳过；**绝不写入**对方数据库 |
| 3 | **隐私面扩大**：这些是私人对话 | 中 | 全部本地解析、**不上传**；来源默认关闭，由你逐个显式开启 |
| 4 | 数据量增长（会话会越来越多） | 低 | 按时间窗（默认近 N 天）+ 条数上限；L2 只读索引不读全文 |
| 5 | Trae 路径含空格与中文（`Trae CN`） | 低 | 路径用 `PathBuf` 拼装，不拼 shell 字符串 |
| 6 | 误把"文件产物"当成"灵感"（噪音） | 中 | L1 需要"来源目录白名单 + 扩展名白名单"，否则全盘搜索结果无法用 |

## 九、待拍板

1. **L2 走不走？** 走 → 同意引 `rusqlite`（推荐）；不走 → 一期只有 L1 + Codex，成本降到 1.5 天。
2. **L3（Codex 全文）一期做不做？** 做 → +1 天，得"我最近在 Codex 里聊了什么"；不做 → 只有话题级。
3. **与已有 automation 的关系**：内容台**消费**它的产出（推荐，零成本），还是把这个采集迁进内容台（成本高、且要重做"什么算灵感"的判断）？
4. **主动调用 Agent** 是否列入下一步（需先有 `runner`）？

## 十、未实测的推断（与结论分开）

以下是**推断**，未实测，不应被当作已定事实：

1. **WorkBuddy 的 `sessions.title` 是否为完整话题** —— 实测样本中，部分 `title` 是**多行正文前缀**（如"（封面页）\r\n智效合一・创见不凡\r\n飞依诺 AI 精英大赛参"），且 `custom_title` 常为 `None`。**取哪个字段、如何截断**需再做一轮验证。
2. **`blobs/` 是否含对话正文** —— 559 个文件，**未逐个探测**。若含，L3 对 WorkBuddy 有机会（但要评估是否明文、是否稳定）。
3. **Trae 云端对话是否有本地缓存** —— 只确认了 `chat_sessions/` 为空 + 存在 `chatHistoryNeedToBeMigrated` 键，**未排除**其他缓存位置。
4. **`logs_2.sqlite`（55MB，在 `.codex/`）** —— 未探查内容，可能含更完整的历史（若含，Codex 侧的源可比 `sessions/` 更全）。
5. **各 Agent 会话的"灵感密度"** —— 我确认了**能读**，但**没验证读出来的东西质量如何**（多少条能真的转成选题）。这需要跑一次真实采集才知道。

> 第 5 条建议先做：**它一条命令就能出结论，且直接决定 L2/L3 值不值得做。**
